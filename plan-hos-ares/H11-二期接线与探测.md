# H11 · 二期接线与探测（B60–B63）

> **定位**：一期（B35–B59）结项后，剩下"模块在、接线未做"的集成尾巴。
> 全部四批**不依赖容器运行时**，可在当前宿主直接判绿。
> 容器真隔离（E1 / A17 / A3 / A18 / E5）不在此列，见 `H07 B45` 与
> `docs/delivery/final-acceptance-2026-11-04.md §4`。

## 0. 为什么单独成册

一期把 25 批压到"20 绿 / 1 未验 / 1 不做"，但留下了四处**实现了却没被调用**的模块。
这类欠账比功能缺失更危险：`check-plan` 全绿、单测全绿，因为测试只测了模块本身，
没有测"主链路是否真的用了它"。B62/B63 就是把单测覆盖到的函数接进生产路径。

本册的批次卡不并入 `H07`：`H07` 被 `check-plan.cjs` 硬断言为恰好 25 批
（`cardDays.size !== 25` 即红），追加会破坏一期的排期契约。

## B60 · 审批落库与事件〔P0，0.5 人天〕

| 项 | 内容 |
|---|---|
| 目标 | `ApprovalGate.decide()` 从"只改内存 record"变成"落 `approvals` 表 + 写 `task_events`"，让审批成为可审计的唯一写入点 |
| 判据 | A：`decide()` 后 `approvals` 表出现对应行，`state` 与内存一致；B：每次 decision 追加一条 `task_events(kind='approval')`，含 `action_class/state/by/reason`；C：自批（`by == requested_by`）被拒且**拒绝本身也留痕**；D：TTL 过期转 `EXPIRED` 并写 `expired` 事件；E：`task_events` 只增不改，自检 5/11/17 仍绿 |
| 产出 | `veripen_core/guard/approval.py`（增加可选 `store` / `events` sink）+ `tests/unit/test_approval_persistence.py` |
| 依赖 | 无（`veripen_core/store.py:171` 的 `approvals` 表已建） |
| PR | `b60/approval-persist` |
| 回滚 | 单提交 revert；`approval.py` 的 sink 参数默认 `None`，旧调用方零改动 |

**为什么不是"审批页面"**：B54 已交付审批界面与"唯一写入点"语义，但它写的是内存态。
没有落库，重启即失忆，审计节拿不到审批证据。

## B61 · doctor 三项探测〔P1，0.5 人天〕

| 项 | 内容 |
|---|---|
| 目标 | `cmd_doctor` 补 `sandbox` / `tui` / `browser` 三项探测，**缺条件记 `skip` 不记 `fail`** |
| 判据 | A：无 docker/podman 时 `sandbox=skip`，`doctor` 总体仍 green；B：有运行时 `sandbox=ok` 并报出二进制路径；C：无 `curses` 时 `tui=skip`；D：无 chromium/playwright 时 `browser=skip`；E：`--json` 输出含三项且 `by_status` 计入 skip |
| 产出 | `veripen_cli/cmd_doctor.py` 三个 `check_*` 函数 + `tests/unit/test_doctor_probes.py` |
| 依赖 | `veripen_core/sandbox/runner.py:126 select_executor()`（判据来源，不重复探测逻辑） |
| PR | `b61/doctor-probes` |
| 回滚 | 单提交 revert；三项各自独立函数，删除不影响既有 11 项检查 |

**判据 A 是重点**：一期 parity 的 `E1` 靠 `shutil.which("docker")` 判 `UNVERIFIED`，
doctor 若把同样条件记成 `fail`，会出现"工具说环境坏了、parity 说只是没验"的矛盾。

## B62 · L1a 压缩接线〔P1，1.0 人天〕

| 项 | 内容 |
|---|---|
| 目标 | 把 `AssetFacts.injectable()` 的事实压成一段带前缀的 L1a 文本，真正进上下文；`compression.compress()` 从"只被 parity 调用"变成生产路径 |
| 判据 | A：`injectable()` 出现非测试调用方（`grep -rn 'injectable('` 命中生产模块）；B：同一输入的 `tokens_after / tokens_before ≤ 0.70`（降幅 ≥30%）；C：改动 L1a 注入内容后，`verdicts_fingerprint` 逐字不变；D：注入条数 ≤10 且每条带 `capsule_id`，无出处的条目剔除；E：过期事实标 `stale` 而不是删除 |
| 产出 | `veripen_core/blackboard.py`（`Fact`/`AssetFact` 字段映射）+ L1a 段组装函数 + `tests/unit/test_l1a_injection.py` |
| 依赖 | `blackboard.py:493 injectable()`、`compression.py:107 compress()`（两者签名已现成） |
| PR | `b62/l1a-compress` |
| 回滚 | 单提交 revert；L1a 段为空时退回"不注入"，与一期行为等价 |

**两条要盯的坑**：`Fact`（`blackboard.py:37`）与 `AssetFact`（`:353`）是不同 dataclass，
需要显式字段映射，不能靠属性名蒙混；`injectable()` 已做 `from_target` 排序与 TTL 过滤，
外层不得重排，否则跨任务记忆的优先级契约失效。

## B63 · plugin knowledge 进 L2〔P1，1.0 人天〕

| 项 | 内容 |
|---|---|
| 目标 | 插件通过 `PluginSpec.knowledge` 声明的文档，转成 `KnowledgeDoc` 进 L2 段；卸载即从 L2 消失 |
| 判据 | A：`with_knowledge()` 出现生产调用（非 `cmd_plugin_roundtrip` 与测试）；B：装 100 条 knowledge 后 `verdict_fingerprint` 与装 0 条相同；C：改 knowledge 全文，指纹仍逐字不变；D：每步 ≤2 条、每条 ≤1KB，超限截断并记账；E：卸载插件后 L2 段不再出现该插件正文，且 `assert_no_leak` 全程不触发 |
| 产出 | `veripen_core/context.py`（`PluginSpec.knowledge` → `KnowledgeDoc` 桥）+ L2 组装处接线 + `tests/unit/test_knowledge_wiring.py` |
| 依赖 | `context.py:110 with_knowledge()`、`plugins/lifecycle.py:37 knowledge`（字段已存在） |
| PR | `b63/knowledge-l2` |
| 回滚 | 单提交 revert；`with_knowledge` 返回原 `Context` 的分支保留，等价于未接 |

**为什么先于判定链**：knowledge 的三条红线（只进 L2、verdict 无关、限额）在
`test_knowledge_redline.py` 已有 12 条用例，接线本身是低风险的；延迟它等于让
"能用插件扩展能力"这条产品叙事继续停在自检命令里。
