## 1. 响应头四件套在 `run` 里没有合法入口

**事实**（B381 实测）：

- 四个 oracle 只选 `html_document`：`hos_ares_oracles/tier_headers.py:129`、`:175`、`:192`、`:215`；
- 这个标签**不在**操作员可选字表里：`hos_ares_core/stream.py:177` 的 18 个标签没有它；
- 于是契约里写它会被直接拒：`契约拒绝：未知标签（html_document）（字典 18 个）`；
- 走结构发现也够不到：`--discover` 从根页爬（本机靶场根页 404×3），且与 `--openapi` 互斥；
- 它其实是**结构推断标签**：`hos_ares_core/routes/tagging.py:57` 在 content-type 是 HTML 时自动加。

| 选项 | 代价 | 影响面 |
|---|---|---|
| A. 把 `html_document` 加入 18 §6 字表（18 → 19） | 字表是冻结的对外契约，加一项要同步改 `plan-hos-ares/18` 与本文；操作员从此可以手写这个标签 | 契约面 +1 项，向后兼容 |
| B. 允许"契约声明 + 结构确认"二选一 | 需要定义"结构确认"的判据（一次 GET 看 content-type？算不算已确认）；实现比 A 大 | 校验逻辑改动，字表不动 |
| C. 维持现状：四条只在 bench 里跑 | 对外宣称"能测缺失安全响应头"，产品路径其实跑不到——**这是当前状态，也是最坏的状态** | 无代码改动 |

**建议**：A（改动最小、语义最直白）。若定 A，代码改动 = 字表加一项 + `plan-hos-ares/18` 同步 + 一条回归测试。

## 2. `set-cookie` 脱敏 vs 会话固定证据可复现

**事实**：

- B376 接入的 `session_fixation` 判据要看 `Set-Cookie` 的会话 id；
- B381 把 `set-cookie` 加进脱敏表：`hos_ares_core/evidence.py:33`——值落盘即等于把登录态写进证据；
- 结果：会话固定的证据**能证明"这次判过"，但不能被第三方重算出同一个结论**。

| 选项 | 代价 | 影响面 |
|---|---|---|
| A. 维持脱敏 | 该 oracle 的重放会落 `predicate_not_recomputable`（六态里的 FAILED） | 可审计性打折，安全性优先 |
| B. 存哈希不存原文（`sha256(sid)` + 是否相同） | 重放能验"两次是不是同一个 id"，但验不出"是不是我给的固定值"；证据不能再现原值 | 需扩证据 schema，重放逻辑分叉 |
| C. 存原文 | 证据文件变成凭据载体 | 安全红线，不建议 |

**建议**：B（存"是否等于我方固定值"这一个布尔 + id 的哈希），既保可复现又不落凭据。

## 4. `requires` 的满足表要不要收紧

**事实**：

- `hos_ares_oracles/common/harness.py` 的 `unmet_requirements` 是**保守表**：未知前缀一律按不满足（fail-closed）；
- B378/B379 之后 `auth:secondary` 与 `oob:listener` 才第一次可满足，此前恒为 false；
- 现在 22 个 oracle 的 requires 全部可由 `run` 满足，但这依赖操作员**记得**给 `--token-secondary` / `--oob`；
- 默认（不带 `--strict-requires`）时，缺输入不会 BLOCKED，而是跑出 `symbol_missing:*` 之类的次生理由。

| 选项 | 代价 | 影响面 |
|---|---|---|
| A. 默认 strict 化（缺输入就 BLOCKED） | bench 的 44 例与既有档位行为都会变，要重新基线 | 行为变更，影响所有用户 |

| C. 维持现状 | 缺输入的表现是次生理由，读者要会翻译 | 现状 |

**建议**：B（信息可见、行为不变）。

## 6. bench 语料要不要覆盖「不带凭据被拒」的授权面

**事实**（B388 实测）：

- 靶场里 `object_read` 面（`/api/items`）**不带凭据也是 200**，`content_read`（`/api/notes/all`）同样；
  只有 `admin_function`（`/api/admin/audit`）与 `protected_read`（`/api/me`）会 401；
- 于是 44 例里没有一条真正测到“401 基线”的场景；
- 把 `baseline_accepts_denied` 开给 `idor_cross_account` / `bola_functional` /
  `xss_stored_probe` / `mtls_required` 再跑 44 例：**判定变化 0/44，reported 41 → 41**——开关是惰性的；
- 逐类核语义后只有一个真正适用：`mtls_required`（它只看 TLS 层放不放行）。
  `idor_cross_account` 的基线要求 body 里出现 `"owner"`（要拿基线当“对象长什么样”的参照），
  401 给不了；`bola_functional` 要求高权 200。两者都不适用 4xx 基线。

| 选项 | 代价 | 影响面 |
|---|---|---|
| A. 让靶场的 `object_read` / `content_read` 面在无凭据时返回 401 | 44 例里多条会从 VERIFIED 变 BLOCKED/REFUTED，bench 数字要重新基线 | 靶场保真度 ↑，历史数字作废 |
| B. 新增“授权面”用例（不删旧例），把 401 基线场景纳入 | 语料从 44 涨到 50+，要与 10 §1 的冻结规矩对齐 | 覆盖 ↑，分母变 |
| C. 维持现状，只在账本里记明“语料不含 401 基线场景” | 读者可能以为越权类被测过了 | 现状 |

**建议**：C 先落地（已在 B388 记录），等 §3 的语料口径一并裁——两者是同一件事。

## 7. harness 要不要支持「多步序列」

**事实**（B392 实测 + 读代码）：

- 现在一个变体只发**一次**请求，`plan(binding)` 也拿不到上一次的响应
  （`hos_ares_oracles/common/harness.py` 的 `run()`：`baseline` → `plan` → 逐变体 `send`）；
- 于是三条判据写得出、却跑不了：
  - **S3 登出失效**：登录 → 登出 → 用旧会话请求（三次请求、两个状态依赖）；
  - **O4 PKCE**：带 `code_challenge` 取码 → 用 `code_verifier` 换码（第二跳要用第一跳的结果）；
  - **O8 scope 越权**：限定 scope 换 token → 拿它访问超范围功能（同上）；
- 三者已在矩阵里单列成 `NEEDS_SEQUENCE`，与"只有清单"互斥——**不是没写代码，是执行模型装不下**。

| 选项 | 代价 | 影响面 |
|---|---|---|
| A. 给 oracle 加"序列"能力（`steps=[...]`，后一步可引用前一步的响应字段） | harness 的 `run()` 要重写一段核心流程，`three_way_holds` 的"一个变体一次请求"前提要重新定义 | 大，但一次解决三条 |
| B. 只加"变量传递"（`{{from:step1.body.token}}`），序列仍写成多个变体 | 变体之间要能共享状态，仍需改 `apply()` 与 `run()` | 中 |
| C. 维持现状，三条留在 `NEEDS_SEQUENCE` 清单里 | 会话生命周期、PKCE、scope 三块能力对外只能写"未支持" | 小 |

**建议**：C 短期（诚实标注），A 中期（这三条都是 OAuth 的核心面，不做等于认证体系缺三分之一）。

## 9. 决策包（B403 实测数字）

每条决策下面是**查过的数**，不是估算。读完可以直接拍。

### §1 `html_document` 进不进契约字表

**先纠正一个我写错过的说法**：这 4 个 oracle（`csp_absent` / `frame_opt_absent` /
`hsts_absent` / `nosniff_absent`）**不是"跑不了"**——结构发现侧早就能选中：

```
infer_tags(method="GET", content_type="text/html") → ('html_document',)
```

也就是说 `--discover` 路径上它们可跑，**只有契约路径写不进去**。之前的披露话术
（"在产品路径选不中"）把发现路径也算成没戏，已在 B403 改为两行分开写。

| 选项 | 收益 | 代价 |
|---|---|---|
| A. 字表 18→19，允许契约里声明 `html_document` | 契约路径可跑这 4 个 | 冻结面变更；要定"契约声明算不算证据"（契约说它是 HTML，实际可能不是） |
| B. 维持现状，只靠 `--discover` | 零风险 | 客户用契约交付时看不到响应头检查，需在报告头写清"这类面要开发现模式" |
| C. 从契约**响应示例**推断（`content` 里若是 HTML） | 无字表变更 | 推断本身可能错，且 OpenAPI 的 response example 常缺 |

**建议 B**：报告已经会说"需 --discover"（B397/B403 已落）；A 的语义争议（契约声明 vs 实测）比它带来的 4 个 oracle 更贵。

### §2 `set-cookie` 脱敏 vs 可复现

现状：整个头脱敏 → 会话类判定（S1/S2）的证据只剩属性名，**重放不出那个 cookie**。

| 选项 | 收益 | 代价 |
|---|---|---|
| A. 维持整体脱敏 | 零泄露风险 | 会话证据只能证明"当时缺 HttpOnly"，不能重放 |
| B. 值脱敏、属性保留 | 证据可读（属性齐全），仍不含凭据 | capsule schema 微调 + 脱敏断言改 |
| C. 不脱敏 | 完全可复现 | **不可接受**：交付物里带客户会话凭据 |

**建议 B**：本轮 S2 判定的证据里"属性名列表"其实就是 B 的一部分，只是没落成字段。

### §3 语料 14 → 17/22 类

现状数字：**44 用例 / 14 类**；注册 28 个 oracle，**14 个没有语料**。

| 选项 | 收益 | 代价 |
|---|---|---|
| A. 扩到 17 类（加响应头 4 个之一或 auth 3 个） | recall 覆盖变宽 | 每类至少 2 例（正+负）→ 约 +6 例 |
| B. 扩到 22 类（把已实现的全覆盖） | recall 能代表产品能力 | +14 类 × 2 例 ≈ 44→72 例，bench 时间翻倍 |
| C. 维持 14 类，只在输出里点名缺失 | 零成本 | 客户问"recall 0.93 覆盖了什么"时答案是"14 类" |

**建议 A**：先加**认证 3 类**（`session_fixation` / `code_replay` / `cookie_flags`）——它们都有真实靶场面，正负例都能造；响应头 4 个等 §1 定了一起做。

### §4 `rate_limit_absent` 默认开还是关

现状：默认关 → 它的 2 条用例是 INCONCLUSIVE → **recall 0.93 里的那 2 个 FN 就是它**。

| 选项 | 收益 | 代价 |
|---|---|---|
| A. 打开 | recall 可到 1.00，且限速检测真会被测 | bench 变慢（限速探测要等于等窗口） |
| B. 维持关 | bench 快 | recall 天花板 0.93，且每次都要解释这 2 个 FN |

**建议 A 但只在 bench 里打开**（`--oracle rate_limit_absent`），产品路径仍按标签选；这样 recall 数字不再带解释。

### §6 语料要不要覆盖 401 基线

现状：44 例里 **0 例**基线是 401 → `baseline_accepts_denied`（B387 加的）在语料上**完全没被触发**（A/B 实测 0/44 变化）。

| 选项 | 收益 | 代价 |
|---|---|---|
| A. 加 2–3 例 401 基线面 | 这个能力第一次被语料验证 | 靶场要加一个"无凭据 401"的读面 |
| B. 不加 | 零成本 | 该能力只靠单测覆盖，语料给的信心是 0 |

**建议 A**：靶场加一个 `/portal/me`（无凭据 401）即可。

### §7 harness 支不支持多步

现状：**3 条认证核心面**（S3 登出失效 / O4 PKCE / O8 scope 越权）判据写得出、跑不了。

| 选项 | 收益 | 代价 |
|---|---|---|
| A. 加 `steps=[...]`（后一步可引用前一步响应字段） | 解锁 3 条，且今后所有多步判据都能写 | `harness.run()` 核心流程改动；`three_way_holds` 的"一个变体一次请求"前提要重定义 |
| B. 只加变量传递（`{{from:step1.body.token}}`） | 解锁同样 3 条 | 仍要改变体间状态共享，改动量接近 A |
| C. 维持现状 | 零成本 | 会话生命周期 / PKCE / scope 三块能力对外只能写"未支持" |

**建议 A**：这三条都是 OAuth 的核心面，不做等于认证体系缺三分之一；而且 B 的改动量并不比 A 少。

**已落地（B410–B412）**：B410 加 `SequenceStep` / `capture_value` / `run_sequence`（各步可打不同端点、
可读上一步响应、端点缺失时如实 `missing_face`），S3（登出失效）与 O4（PKCE）随即接入；
B412 接 O8（scope 提升）后 `NEEDS_SEQUENCE` 清零。实际成本是 **3 批**，不是 8–12 批——
估计偏高的原因写在账本 B410/B411：前两批撞的全是"结构性"坑（同端点冒充、RouteSet 绝对地址、
非幂等默认值），坑填完之后第三个 oracle 只加了一个文件。

**建议 B**：分段只改 CI 编排，不改用例；并发化要处理端口与靶场冲突，成本高一个量级。

现状：`.venv/` 被 gitignore，仓库里没有「一条命令建好它」的入口（B367）；新人靠文档拼。
