## B81 · chat 接真模型路径〔P0，1 人天〕

| 项 | 内容 |
|---|---|
| 目标 | 配了 `VERIPEN_MODEL_BASE_URL` + `VERIPEN_MODEL` 时，chat 的每句话先问模型；模型给不出合规调用时**降级 rules 并明说** |
| 判据 | A：模型返回 `{"tool":"read","args":{"path":...}}` 时被采纳并执行（不走 rules）；B：模型返回非法（未知工具 / 多调用 / 缺 args）时降级 rules，且界面显示"模型不可用，已降级"；C：未配置模型时仍走 rules（与 B77 逐字一致）；D：横幅如实显示当前决策层；E：只连 loopback（测试用本地假服务） |
| 产出 | `veripen_cli/cmd_chat.py`（模型分支）+ `tests/lab/model_server.py`（OpenAI 兼容假服务）+ `tests/integration/test_chat_model.py` |
| 依赖 | `agent/client.py`（`HttpChatClient` / `to_tool_call`）、`agent/intent.py`（降级目标） |
| PR | `b81/chat-model` |
| 回滚 | 删掉模型分支；rules 路径不动 |

### 为什么用假服务而不是真模型

本机没有模型后端（`~/.litellm` 不存在、4000 不通）。但**链路正确性**可以验：

假服务按 OpenAI 协议返回固定 JSON，能证明四件事：

1. 请求格式对（`/chat/completions`、`response_format=json_object`、`tools` 字段）；
2. 响应解析对（`choices[0].message.content` → JSON → `ToolCall`）；
3. 窄 schema 不误拒（合规的 `{"tool","args"}` 能被接受）；
4. 非法响应能降级（不是崩，而是退回 rules 并说清）。

**证明不了**的是"真模型会不会服从窄 schema"——那是模型能力问题，
本地假服务给不了答案。这条要写进结论，不许含糊。

### 降级的三种情形

| 情形 | 行为 |
|---|---|
| 未配置模型 | rules（横幅 `model: rules`） |
| 配置了但请求失败（超时/连接拒绝/非 200） | rules + **界面提示"模型不可达，本轮用规则"** |
| 配置了但响应非法（未知工具/多调用/缺字段） | rules + **提示"模型返回不合规，已降级"** |

三种都要能一眼区分——"模型坏了"和"模型没配"是两件事。

### 与 `agent`（B67）的分工

`agent` 走的是 `Loop` + `ModelDecider`，那是**判定链路**里的模型（一步一 oracle）。
`chat` 是**工作台/渗透/编排**的对话入口，模型只负责"这句话该调哪个工具"。

两者都用 `HttpChatClient`，但 `chat` 不碰 `Loop` 的 `tool_calls_per_step` 纪律。

## 执行记录（2026-11-05）

实测（本地 OpenAI 兼容假服务）：

| 情形 | 结果 |
|---|---|
| 模型返回 `{"tool":"read","args":{"path":"notes.txt"}}` | ✅ 被采纳并执行（不走 rules） |
| 请求形状 | ✅ `POST …/chat/completions`、带 tools/response_format、model 名对 |
| 未知工具 `no_such_tool` | ✅ 降级 rules + 提示"模型未给出合规调用" |
| 两个调用 | ✅ 被拒（一步一调用） |
| 服务 500 | ✅ 降级，不崩 |
| 未配置 | ✅ `model: rules`，无降级提示 |

判据 A–E 全绿：`test_chat_model.py` 7 passed。

**期间发现并修的一处真缺陷**：最初用 `to_tool_call` 校验模型调用，
但它的白名单是 `SCHEMAS ∪ surface_names()`（面向判定链路的 oracle 工具），
**`read` 不在里面** → 合规的模型调用被判成非法、全部降级。
改为按 chat 自己的工具集（`CHAT_TOOLS`）校验：用错表会把对的判成错的。
