# H18 · 报告"面"的显示（B74）

> **缺陷**：报告里每条发现的"面"显示成 `route://` —— 只有 scheme，没有可辨识部分。
>
> 根因：`FindingView.route_short` 取 `route_ref[:8]`，而 `route://` 恰好就是 8 个字符。
> 截断位置正好落在分隔符之后，于是**所有发现的"面"长得一模一样**。

## B74 · `route_short` 保留可辨识段〔P2，0.5 人天〕

| 项 | 内容 |
|---|---|
| 目标 | 报告/markdown/sarif 里的"面"显示成 `route://contract/e27578ec` 形态：保留 scheme 与来源，截断不透明 id |
| 判据 | A：`route://contract/<16hex>` 显示为 `route://contract/<前16位>`；B：**不含** scheme 的 ref 仍按前 8 位截断（行为不变）；C：空 ref 显示空串（渲染层自己补 `-`）；D：脱敏不放松——仍不透出完整 id，只是把"来源"露出来 |
| 产出 | `veripen/report/render.py`（`route_short`）+ `tests/unit/test_report_route_short.py` |
| 依赖 | 无 |
| PR | `b74/route-short` |
| 回滚 | 单行 property 改动，可独立 revert |

### 为什么不是"直接显示完整 ref"

完整 ref 是 `route://contract/<64 hex>`，进报告会让每行多 60 字符，
且**不透明 id 本身没有阅读价值**——读者要的是"这条面来自契约还是观测"。

所以显示策略是：**保留来源段 + 截断 id**。信息量从 0 变成 1（能区分 contract / observed / crawl）。

### 影响面

`route_short` 被四处使用（json / sarif / markdown / 未验证节），改一处全生效。
这也是选它而不是在每个渲染点各改一次的理由。

## 执行记录（2026-11-05）

| 项 | 结果 |
|---|---|
| 修复前 | 报告里所有面都是 `route://` |
| 修复后 | `route://contract/5ab365e3`（来源段 + id 前 8 位） |
| 测试 | `test_report_route_short.py` 5 passed；全量 unit 绿 |

实现细节：`route_short` 现在按 `scheme + source/ + id[:8]` 拼，而不是整体截 8 位。
无 scheme 的 ref 仍走原逻辑（前 8 位），行为不变。
