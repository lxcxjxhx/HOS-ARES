## 2. B50 · Playbook 资产库（2 人天）

### 2.1 最小资产集（不贪多，三个就够证明"资产化"成立）

| id | 适用面 | 关键顺序 | 常见坑 | 成功判据 |
|---|---|---|---|---|
| `idor-enum-first` | `idor_cross_account` / `bola_functional` | 先列表接口拿真实 id → 低权账号试 → 再用"不属于自己的 id"当对照 | 直接猜 id 会拿到 404，误判为"不存在" | 三条绑定命中且 `control` 成立 |
| `sqli-waf-probe` | `sqli_bool_diff` / `sqli_error_based` | 无害 payload 探 WAF → 编码变体 → 布尔差分 | WAF 拦掉的响应被当成"无注入" | 差分显著且 baseline 稳定 |
| `ratelimit-window` | `rate_limit_absent` | 先单发取基线 → 固定窗口内 N 发 → 观察第 N+1 | 把 429 当"有防护"（可能是 CDN 默认） | 窗口内成功率随 N 变化 |

### 2.2 规则（2026-11-04 B50 落地）

> 三个资产已入库：`playbooks/pb-idor-enum-first.yaml`、`pb-sqli-waf-probe.yaml`、`pb-ratelimit-window.yaml`；
> 校验：`python -m veripen_cli.cmd_playbook check`（schema + oracle/impact + 成功率必须等于实测）；
> 演练：`python scripts/b50/playbook_run.py --rounds 5` → `playbooks/measured.json`
> （**内存夹具靶，`rehearsal:true`**；SQLi 在夹具上不成立 → 0.0，负数照写）。

| 规则 | 内容 |
|---|---|
| 格式 | `playbooks/<id>.yaml`，遵循 `plan-veripen/schemas/playbook.schema.json` |
| **成功率必须实测** | `success_rate` 由 `make playbook-run` 真跑得出，**不许手填**；样本 < 5 次记 `insufficient` |
| 不产判定 | playbook 只产 lead/动作序列，verdict 仍由 oracle 给（H1） |
| 可追溯 | 每条 playbook 带 `applies_when`（标签表达式）与 `source`（专家经验/复盘/公开资料） |
| 不写地址 | playbook 里只能是语义标签与动作，不许出现 host/path（H2） |

**判据**：`make playbook-check` —— schema 通过 + 三个 playbook 各跑 ≥5 次 + `success_rate` 与实测一致；
把 `success_rate` 手改一个数 → 红。

## 3. B51 · 黑板冲突消解与事实溯源（2 人天）

> **执行记录（2026-11-04）**：`Blackboard.resolve()` 按 (来源等级, 观测时间, 写入序) 取一条 live，
> 其余 `superseded` 且**不删除**；`injectable()` 只注入胜出者；`conflict_report()` + 
> `veripen/report/render.py:render_conflict_table()` 产出确定性冲突表。
> **缺口（照实记）**：绑定置信目前不在事实里（`RouteBinding.confidence` 不进黑板），
> 排序键只有两级；冲突表已能渲染，但**尚未接进 markdown 报告排版**（B53 一并接）。

现在的 `disputed()` 只回答"这两条事实互相矛盾"，没人用它。要补三件事：

| 补什么 | 规则 |
|---|---|
| **消解规则** | 冲突按 `(来源等级, 观测时间, 绑定置信)` 排序取一条为 `live`，其余标 `superseded`，**不删除**（只增不改） |
| **注入排序** | `injectable()` 从"最近 30 条"改为"按 (相关性, 新鲜度, 冲突状态) 打分取 30"，相关性由当前 pending oracle 的标签决定 |
| **进报告** | 每份报告附"事实冲突表"：哪两条冲突、谁胜出、为什么——**这一节能直接回答"AI 是不是在乱猜"** |

**判据（A19 的一部分）**：造两条互斥事实 → `live` 只有一条、`superseded` 保留；把消解规则删掉 → 红。

## 4. B52 · 上下文压缩算法（2 人天）

> **执行记录（2026-11-04）**：`veripen_core/compression.py` 落地三种算法——
> 事实摘要（按 `(subject,predicate)` 合并，`merged_from` 可回溯）、步骤摘要（≤5 行 + 更早计数）、
> 证据按需（默认只放 capsule id，`expand()` 只加载点名的那几个）。
> 红线可执行：`verdicts_fingerprint` 由调用方传入并原样返回；回落 `summarize=False` 只裁剪，
> 指纹同样不变。实测：20 条事实 + 20 步事件 → token 降幅 ≥30%。

现状是"丢文档"，目标是"压事实"。三条最小算法（够用即可，不追论文）：

| 算法 | 输入 | 输出 | 判据 |
|---|---|---|---|
| **事实摘要** | 黑板中同 `(asset, kind)` 的多条事实 | 一条带 `merged_from` 的摘要事实 | 摘要后仍能回答"这个资产是什么栈"，且 `merged_from` 可回溯 |
| **步骤摘要** | 最近 N 步的 `task_events` | ≤5 行摘要（动作/结果/影响） | 压缩前后 `verdict_fingerprint` 相同（不得改判定） |
| **证据按需** | capsule id 列表 | 只在需要时展开全文 | 压缩后 token 数下降 ≥ 30%，判定不变 |

**硬规则**：压缩只作用于**上下文**，不作用于**证据**与**判定输入**（`17 I1/I2`）。
判据必须包含"压缩前后同一任务的 findings 逐条相同"。

## 5. B53 · 报告"智能体行为审计"一节（1 人天）

`plan-veripen/32 §3 A4` 提过但没落地。五张小表，数据全在 `task_events` 里，几乎是免费的：

| 表 | 列 |
|---|---|
| 动作账 | 时间 / 动作 / 目标（语义面）/ 影响级 / 是否审批 |
| 预算账 | 五预算各自用量与上限 |
| 拒绝账 | 被 guard 拦下的动作 + 原因码 |
| 冲突账 | 事实冲突与消解结果（来自 B51） |
| 异常账 | 解析失败/超时/降级次数 |

**判据**：同一任务的报告两次生成，五表逐行相同（确定性）；少一张表 → 红。
措辞纪律：这一节只陈述"做了什么"，**不评价"做得好不好"**（评价属人工复核）。

## 6. B54 · 审批与观察队列界面（1.5 人天）

> **执行记录（2026-11-04）**：`ui.approvals`（第 10 页）落地——GET 列表带 TTL 与 8 位绑定，
> POST 是控制台**唯一**写入点：批准/拒绝必填理由、自批（`decided_by == lease_owner`）403、
> 1h 过期 409、重复决策 409；其余 `ui.*` 写方法仍 405（契约测试加了"唯一例外"断言）。
> 拒绝理由进报告附录（`render_audit_section` 的新增小节）。

现状：审批只有工具调用（`RequestApprovalCall`），控制台没有页面（9 页里没有 approvals）。

| 项 | 内容 |
|---|---|
| 页面 | 新增 `ui.approvals`（第 10 页），列出待批动作 |
| 每张卡片 | 动作性质（只读/写/扫描）、影响资产（语义面）、预计请求数、可逆性、绑定摘要（8 位）、超时倒计时 |
| 操作 | 批准/拒绝 + 必填理由（这是**唯一**允许写的地方） |
| 写边界 | `ui.approvals` 的 POST 是**唯一例外**：只写审批决定，不写发现、不改 verdict；其余 `ui.*` 仍 405 |
| 判据 | ① 非审批路径仍 405 ② 自批被拒（`decided_by != lease_owner`）③ 1h 过期自动 `EXPIRED` 并在页面消失 ④ 拒绝理由进报告附录 |

> **红线段落**：这条会打破"控制台完全只读"。破例必须写进 `H10` 与 `plan-veripen/22 §1` 的修订记录，
> 且类型上限定为"审批决定"这一种写入。**不许顺手加别的写接口。**
