# 量具失误形态清单（27 轮实战归纳）

> 这不是一份"经验总结"，是一份**写新量具前逐条扫一遍**的清单。
> 每条都来自一次真实的假故障——量具报了个"产品缺陷"，查下去发现量具自己错了。
>
> 归纳自 `.hos-ares/batches.jsonl` 的 B539 / B555 / B556 / B557 / B562 / B565 / B566。

---

## 为什么单独成文

27 轮里**至少 7 次**，我报出的"缺陷"是假的：

| 批次 | 量具报了什么 | 真相 |
|---|---|---|
| B539 | "卸载有残留" | 卸载前没停进程，Windows 删不掉在跑的 exe |
| B539 | "页面没有导航" | 只读了前 4 KB，`id="nav"` 在 30 KB 页面的样式表之后 |
| B555 | "所有 GET 都 404" | `build_app()` 调了两次，路由表与请求实例不同 |
| B555 | "审批页 GET 404" | `chr(0x2F) + "ui.approvals"` 拼出 `/ui.approvals` |
| B556 | "链头 prev 不是全零（链坏了）" | 按文件名排序喂 `verify_chain`，喂错顺序 |
| B556 | "删了环也没事" | 验的是被截断的子链，只校它收到的部分 |
| B557 | "步骤没落库" | 按传入的 `--task-id` 查库，而首轮自动生成 ULID |
| B562/B565 | "文档数字与实测不符" ×2 | 把**环境分配**当成**能力**（CI 无 podman） |
| B566 | "多调用仍被拒" | `(*MUST_FALLBACK, *MUST_ACCEPT)` 把 str 拆成单字符，那个 mode 一次没测 |

**七次里有五次，是同一个模式：我的量具对被测接口做了错误假设。**

## 六种形态（写新量具前扫一遍）

### 1. 排序假设
**症状**：拿到的集合顺序与你以为的不同。
**实例**（B556）：按文件名排 capsule（文件名是内容哈希，与链序无关）。
**防法**：**不要假设顺序**。需要顺序就从数据本身重建（如 `prev → self` 串链）。

### 1b. 路径/格式假设
**症状**：量具数出来恒为 0（或全都"符合"），因为比较的两个字符串形式不同。
**实例**（B570）：`type_debt.py` 拿 `ln.startswith("scripts/")` 过滤 mypy 输出，
而 Windows 上 mypy 打的是 `scripts\xxx.py`（反斜杠）——**74 个错误数成 0**。
**防法**：跨平台比较前先归一化分隔符；量具的第一次运行必须**能数出非零**（见形态 6）。

### 2. 截断假设
**症状**：读了一部分就说"没有"。
**实例**（B539）：只读前 4000 字节判"页面没有 nav"。
**防法**：判"存在性"必须读全；要截断时在**断言里写明**"我只看了前 N 字节"。

### 3. 实例/身份假设
**症状**：两次构造的对象不是同一个。
**实例**（B555）：`build_app()` 调两次：路由表来自 A、请求打到 B。
**防法**：需要"同一个"就用一个变量；`_paths(app)` 与 `TestClient(app)` 用**同一个 app**。

### 4. 环境假设（最容易反复犯）
**症状**：在本机成立、在 CI 不成立（或反过来）。
**实例**（B562 / B565）：parity/doctor 的数字、容器执行体是否存在。
**防法**：先列出**哪些量会随环境变**。
- **常量**（能力项 22、检查项 25）→ 可以精确断言
- **分配**（ok/skip 各多少、green/未验各多少）→ **只能验不变式**
**并且**：写完立刻在**两种环境**各跑一遍。模拟环境**过严和过松一样有害**（B565：禁掉 JobObject 导致模拟比真 CI 更严）。

### 5. 参数化假设
**症状**：你以为传了 A，实际生效的是 B。
**实例**（B557）：`--task-id` 首轮不生效（`--help` 写着"（`--resume` 时指定）"，是我没读）。
**防法**：**先读 `--help` 和 docstring**；需要"某参数生效"时，从**结果**里反查（如从库里读真实 id）。

### 6. 列表/展开假设
**症状**：你测的那个 case 一次都没跑。
**实例**（B566）：`(*MUST_FALLBACK, *MUST_ACCEPT)` 把 `"two_calls"` 拆成单字符。
**防法**：**量具要证明"它测到了"**——跑完读回结果，确认每个 case 都有非空输出（`None` / 缺失键是信号）。

## 三条硬规矩

### 规矩一：先写判据，再写量具

**判据写"客户该看到什么"，不是"某个字段该等于什么"。**

| 判据 | 量具 |
|---|---|
| ❌ "`installed['p'].version == '1.0.0'`" | 只会读字段，读不出"实现丢了" |
| ✅ "回滚后旧版本**还能被调用**" | 必须真的 `invoke()` 一次 → 抓到两个真缺陷（B558） |

27 轮里，"先写判据"那三轮（B558/B559/B560）**第一次跑就抓到真东西**；
反过来那几轮量具都在栽跟头。

### 规矩二：量具必须能红

写完先问：**"什么样的缺陷会让这条红？"** 答不上来说明它在测"能不能跑"，不是"对不对"。

可用的做法：
- 伪造一个违反不变式的状态，看判据是否察觉（B559 的 `test_probe_would_catch_a_gate_that_allows_self_approval`）；
- 把关键常量反过来（B560 把 `ORIGIN_RANK` 颠倒）；
- 去掉唯一例外（B555 把 `WRITE_EXCEPTION_PATH` 改成不存在的路径）。

### 规矩三：量具的失败**不是结论**，是线索

看到量具报红，第一步**不是**去改产品，是问：

> "如果产品是好的，哪种量具 bug 也会产生这个输出？"

上面六种形态就是那个问题的答案清单。
