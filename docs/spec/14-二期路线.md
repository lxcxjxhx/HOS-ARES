# 14 · 二期路线与 `core diff = 0` 守则

> 当前企业只是第一步。本文规定"能力怎样长出来而内核不腐化"。
> 唯一的成功指标：**新增一个客户时，`veripen_core/` 的 diff 是否为 0。**

## 1. 能力生长路径

```
一期（本规划）  内核 + 2 档 + 14 oracle + 8 断言（17 批，见 21）
                └ 目标：证明可复用、可交付、可离线

二期            客户 B 接真实资产
                ├ 新增 oracle 插件 1–2 个（业务逻辑差分类优先，车企最关注）
                ├ 新增 profile 1 个
                ├ OpenAPI 解析 → 自动生成越权用例（真正的行业楔子）
                └ 目标：core diff = 0 的前提下多卖一家

三期            白盒与交互式能力
                ├ SARIF in → 可达性验证 → SARIF out
                ├ tree-sitter 抽路由/参数，与 oracle 的 param_signature 对齐
                └ 交互式工具会话管理（tmux + 提示符 + 清理），仅在有授权的场景启用

四期            运营化（续约逻辑所在）
                ├ 误报回灌：人工判定 → usecase → 回归集
                ├ 覆盖率评估：资产 × oracle 的矩阵视图
                └ 告警降噪：与客户 SIEM/工单系统对接（只读+留痕）

五期            规模化（在有第二个付费客户之后才做）
                └ 多租户 / RBAC / K8s / 前端
```

## 2. 每期的验收（不达不进下一期）

| 期 | 验收 |
|---|---|
| 一期 | 5 条断言全绿；bench FP=0、越界=0；断网机器能装 |
| 二期 | 接客户 B 全程 `core/` diff = 0；新 oracle 只新增文件；bench 用例集扩充且回归不退化 |
| 三期 | SARIF in→out 往返不丢告警；白盒发现能与黑盒发现按资产关联 |
| 四期 | 人工判定回灌后，同类误报在下一轮消失（可量化） |
| 五期 | — |

## 3. `core diff = 0` 守则（5 条，写进 CONTRIBUTING）

1. **新客户 → 只加 `profiles/<name>/`**。想在 core 里加 `if customer == ...` 的，直接拒。
2. **新漏洞 → 只加 `veripen_oracles/<id>/`**。若发现"必须改 core 才能加"，说明 `Oracle` 协议漏了抽象 → 这是协议升级（minor 版本），必须连带补协议测试。
3. **新报告规范 → 只加 `report/mappings/<fw>.yaml`**。
4. **新部署形态 → 只加 `deploy/<form>/`**，不改业务代码。
5. **任何 core 改动必须回答三问**：是不是通用能力？有没有客户信息渗入？老 profile 会不会坏？

**机械化检查**

```bash
# 接新客户时跑这个，必须为空
git diff --stat -- veripen_core/ veripen_oracles/ | grep -v '^$'
# 内核零客户串
make lint-noleak     # grep -riE "$(profile 里所有 customer/域名/路径)" veripen_core/
```

## 4. 商业化对应的能力开关（同一个内核，不同合同）

| 客户合同条款 | 落到哪个配置 |
|---|---|
| 只能测指定域名 | `scope.assets` |
| 只能只读测试 | `policy.max_impact_class: read_only` |
| 夜间窗口 | `scope.window` |
| 限速 5 QPS | `policy.qps_global: 5` |
| 报告需含 R155 映射 | `report.frameworks: [un_r155]` |
| 证据不得出机房 | `policy.data_egress: deny` |
| 每次高危需审批 | `policy.approval_gates` |
| 试用期限制资产数 | `meta.env: lab` + 资产条数校验 |

> **销售能改的只有 YAML，改不了代码——这是可交付性的本质。**

## 4.5 成本与报价模型（乙方口径，供报价参考）

### 4.5.1 单轮成本构成

| 项 | 量级（demo 规模） | 说明 |
|---|---|---|
| 模型 token | 20–60 万 / 轮 | 44 例 bench 约 60 万；单客户单轮 20 万量级 |
| 计算 | 3 worker × 30 min | 本地机器，无云成本 |
| 存储 | capsule 2–10 MB / 轮 | 正文摘录 4KB + 元数据 |
| 人力 | 0.5–1 人天 / 轮 | 审报告、复核未验证项 |

**每发现成本** = (token 成本 + 人力) / 已验证发现数。demo 规模约 **每发现 3–8 元 + 0.1 人天**。

### 4.5.2 三档报价结构（对外）

| 档 | 内容 | 计价单位 | 备注 |
|---|---|---|---|
| POC | 单客户单环境、14 类 oracle、1 轮 | 一次性 | 用于验证"能发现并复现" |
| 项目 | 多环境、多轮、报告交付、复测 | 按资产数 × 轮次 | 含合规映射章节 |
| 订阅 | 季度复测 + 误报治理 + 覆盖率报告 + 用例沉淀 | 年费 | 续约点在这 |

### 4.5.3 报价时必须说清的三件事

1. **不含什么**：业务逻辑类、白盒、内网 AD、SAML 自动化 —— 写进合同附件（`16 §7` Parking Lot）。
2. **不承诺什么**：不承诺"零漏报"；承诺"每条发现可复现 + 越界为零 + 误报可回灌"。
3. **加价项**：加一类 oracle（半天）、加一个客户档（半天）、加一种合规框架（2 小时）、离线包定制（1 天）。

## 5. 与"竞争与替代"的定位（对外统一话术）

| 客户说 | 我们的答 |
|---|---|
| "我们有 SAST" | SAST 广覆盖、静态；我们做**可达性验证**，把"疑似"变成"可复现"，不替代 |
| "我们有 SCA" | SCA 管组件已知漏洞；我们管业务逻辑与授权缺陷 |
| "人工渗透更靠谱" | 我们和人工一致率可达 90%+（差分类 100%），定位是**放大人工、沉淀用例**，不是替代人 |
| "AI 会乱打" | 三处 scope 校验 + 只读默认 + 审批门 + 留痕；越界一次整轮跑分作废 |
| "能不能接我们 SIEM" | 四期能力，SARIF/JSON 已具备接入基础 |

## 6. 从"发现"扩到"运营"（续约逻辑）

```
一期卖：验证能力（一次性项目）
二期卖：新客户/新场景（按客户数）
三期卖：白盒覆盖（按代码量）
四期卖：运营订阅（误报治理 + 覆盖率报告 + 用例沉淀）← 真正的续约点
```

续约的核心论据：**用例集越用越大，客户换供应商的成本越来越高**（数据资产粘性）。

## 7. 面试/答辩时的能力对齐（八块 → 本项目证据）

| 能力块 | 本项目里的证据 | 若被深挖 |
|---|---|---|
| 分布式 | 幂等键 + 租约 + 回收 + 死信 | 讲"不需要 Raft，因为动作要幂等" |
| 渗透 | 14 类 oracle 三条件合取 + 28 正 16 负 | 讲"两个请求能对比的都确定性化" |
| Agent | 判定纯函数 + 双预算 + 工具 schema | 讲"模型只影响效率不影响判定"（bench 可证） |
| 工程交付 | 离线包 + doctor + profile 化 | 讲"客户差异只进配置" |
| 质量评测 | bench 协议 + FP=0 硬门槛 + 人工基线 | 讲"没有 FP 率的效果是自说自话" |
| 数据合规 | capsule 哈希链 + 不出域 + 合规映射 | 讲"最大风险是打到不该打的地方" |
| 人机协同 | 审批门 + 三视图报告 + 反馈闭环 | 讲"是否执行由人决定，责任由人承担" |
| 交付组织 | 四条验收 + 范围换算（加一类漏洞=一周） | 讲"能卖/敢用/能复用，缺一件做不成" |

**口述补的缺口**（不进代码，见 `07 §5` 与对话备忘）：交互式工具自动化、白盒可达性、OpenAPI 批量生成、mTLS 测试点、agent 自身安全。
