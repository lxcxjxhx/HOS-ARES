# 19 · 接口契约与用例生成（契约 → RouteSet → 选择器匹配）

> 为什么必须有这一章：车云有几百个接口，手工写用例不现实。
> 这一章把"给它一份机器可读契约，它自己解析出可测面并跑完"变成可交付的模块。
>
> **v3 重写**：本模块的产出**不是 `cases.yaml` 里的路径**，而是 **`RouteSet` + 选择器匹配结果**。
> 生成器只回答"有哪些面、每面属于哪个语义标签"，**不回答"地址是什么"**（`27`）。

## 1. 模块定位

```
机器可读契约（OpenAPI / GraphQL SDL / proto / 自述 schema）
      │  ← 位置本身由 route_discovery 解析（27 §3.8），不写死
      ▼
┌──────────────────────────┐
│ veripen_contract         │  解析 → 归一化 Operation → 打标签 → 选择器匹配
│  parser / planner        │  （纯函数，无网络，无 IO 除读契约文件）
└──────────┬───────────────┘
           ▼
   OperationSet（op_id / method / 参数形状 / 安全声明 / 标签）
           ▼
   routes.sources.contract  →  RouteCandidate（含 template_sha256）
           ▼
   routes.merge             →  RouteSet（routeset_sha256）
           ▼
   oracle 按 selector_tags 取绑定 → 发请求
```

**关键判断**：契约模块**不产判定、不产地址消费方**。
它把"结构"交给 `routes`，把"选择"交给 profile 的 `selectors`，把"判定"留给 oracle。
三层各管一段，任何一层出错都不会污染可信度。

## 2. 解析（OpenAPI 3.0/3.1 为首要，其余为适配器）

| 输入 | 提取 | 输出字段 |
|---|---|---|
| `paths.*.*` | method, path（**只在本模块内存中存在**）, operationId, tags | `op_id` |
| `parameters` | name, in(query/path/header/cookie), schema.type/format, required | `params[]` |
| `requestBody` | content-type, schema 属性树（含 `readOnly`/`writeOnly`） | `body_schema` |
| `security` | 全局与 operation 级；securitySchemes 类型 | `auth_requirement` |
| `responses` | 2xx 的 schema（用于"正常响应"判定与响应形状） | `success_shape` |
| `x-*` 扩展 | **语义标签**（`x-veripen-tags: [object_read, ...]`） | `semantic_tags[]` |

**归一化**：
- 路径参数统一成 `{param}` 形态（同一资源的 `{vin}` 与 `{id}` 写法归一为同一 `structural_key`）。
- 同名参数合并；同一 `(method, normalized_path)` 只保留最完整的那份定义。
- `servers[0].url` **不作为 base_url 使用**（v2 的做法），只作为"契约自述的根"参与 host 一致性校验。

**拒绝条件**（启动即失败）：
- 契约的 `servers[].url` 的 host **不在 assets 解析集合内** → `VP-1006 CONTRACT_HOST_OUT_OF_SCOPE`
- 操作数 > `max_operations`（默认 500，防撑爆）
- 存在 `$ref` 循环（记录并跳过该分支，不整体失败）
- 标签使用了 `18 §6` 字典里没有的词 → 启动失败（防止标签漂移）

## 3. 打标签（这是 v3 最重要的一步）

标签决定"这个面能测什么"。三种来源，按优先级：

| 来源 | 依据 | 置信贡献 |
|---|---|---|
| 契约显式标注 | `x-veripen-tags`（客户/靶场自己写） | 高（confidence 0.95） |
| 结构推断 | 参数类型/位置、响应形状、安全声明（规则表见下） | 中（confidence 0.80） |
| 观测推断 | 已有流量证据的行为特征（回显、3xx、文件下载） | 中高（confidence 0.85） |

**结构推断规则表（纯函数，无路径语义假设）**

| 标签 | 判据（**只看结构，不看路径文字**） |
|---|---|
| `object_read` | method ∈ {GET,HEAD} ∧ 存在单个 path 参数 ∧ 响应 schema 含 `id` 类字段 |
| `object_list` | method = GET ∧ 存在 `limit`/`offset`/`page`/`cursor` 之一 ∧ 响应为数组或分页对象 |
| `param_injectable` | 存在 query/path 标量参数 ∧ 该参数在 `success_shape` 之外影响响应（由观测补充） |
| `url_fetch` | 存在 `format: uri` 或 `format: url` 参数，或参数名语义匹配（`url`/`uri`/`target`/`webhook`/`callback`） |
| `file_read` | method = GET ∧ 存在字符串参数 ∧ 2xx 响应含 `content-disposition` 或二进制类型 |
| `redirect_entry` | 3xx 出现在 `responses` 里，或存在 `Location` 响应头声明 |
| `echo_param` | 观测：某参数值以原样出现在响应体中 |
| `token_issue` | 响应 schema 含 `access_token`/`token`/`jwt` 之一 |
| `protected_read` | operation 声明了 security ∧ method = GET |
| `profile_write` | method ∈ {PUT,PATCH} ∧ 路径结构含"当前用户自指"语义（`me`/`self`/`profile` 作为**参数值为空的自指段**）∧ body schema 可写 |
| `profile_read` | method = GET ∧ 与某条 `profile_write` 同 `structural_key` 前缀 |
| `admin_function` | operation 的 security 声明要求更高角色，**或**契约显式标注 |
| `normal_function` | 与某条 `admin_function` 共享 body schema 但安全要求更低（对照用） |
| `rate_sensitive` | 契约 `x-veripen-tags` 显式，或 operation 属于 `token_issue` |
| `content_write` / `content_read` | method = POST/PUT ∧ body 含自由文本字段 / 对应的 GET |
| `api_read` | method = GET ∧ 响应 `content-type` 为 JSON |
| `graphql_endpoint` | 请求/响应 `content-type` 含 `graphql` |

> **"路径结构含自指段"是唯一允许看路径字面的地方**，而且它只是**判断"这是不是当前用户的资源"**，
> 输出的是标签，不是地址。实现上：`parser` 把路径段归一成 `literal` / `param` 两类，
> 自指判断只看 `literal` 段的**词表命中**（`me`/`self`/`profile`），词表在 `18 §6` 之外单列，
> 且这份词表**不能用于构造请求**（只用于打标签）。

**为什么允许这一点**：完全不看路径语义会让 `profile_write` 打不出来，而这是 `mass_assignment` 的前提。
限制是"只读不写"：读路径是为了分类，不是为了发送。

### 3.1 标签冲突怎么裁决（三种来源打架时）

一个 operation 上出现三种来源的标签，必然冲突。**必须有裁决规则，否则实现者会各写一套 if。**

**冲突的四种实际形态**

| # | 冲突 | 例子 | 危险方向 |
|---|---|---|---|
| C1 | 契约说 A，结构推断说 ¬A | 契约标 `object_read`，但结构显示没有对象标识参数 | 打空（无害） vs 打错（有害） |
| C2 | 契约说 A，结构推断说 B（互斥） | 契约标 `admin_function`，结构显示无高权要求 | **把普通面管理面化 → 误报 BOLA** |
| C3 | 契约未标，结构推断出高危标签 | 契约没标 `url_fetch`，但参数是 `format: uri` | **多打一个面** |
| C4 | 契约标了，观测否证 | 契约标 `echo_param`，但历史流量里参数从没回显 | 判不出来（INCONCLUSIVE） |

**裁决表（冻结）**

| 来源组合 | 采用 | 理由 |
|---|---|---|
| 契约 ∧ 结构 ∧ 观测 三者一致 | 该标签 | 最高可信，`tag_confidence = 0.95` |
| 契约 ∧ 结构 一致，观测未知 | 该标签 | `0.90` |
| 契约 ∧ 观测 一致，结构不符 | 该标签（**降级**） | `0.80`，且记 `structural_mismatch: true`（进报告附录） |
| **仅有契约** | 采用 | `0.85`；契约是权威，但未经结构/观测确认 |
| **仅有结构** | **不用**（见下） | — |
| **仅有观测** | 采用 | `0.85`；真实发生过的行为比文档可靠 |
| **契约 ∧ 结构 冲突（C2）** | **采用契约，但标 `disputed: true` 并强制走 `probe` 验证** | 见"为什么契约赢" |
| **契约否，结构是（C3）** | **不用结构标签** | 见"为什么结构不能单独成立" |
| 契约 ∧ 观测 冲突（C4） | 采用观测（**实际行为优先**），标 `disputed: true` | 见"为什么观测赢" |

**三条判据（解释上面每一处的不对称）**

1. **结构推断不能单独成立**。结构是"看起来像"，不是"确实是"。
   若允许它单独成立，等于让 parser 猜意图——和猜路径是同一类错误。
   **结构只能：给契约标签加分、给观测标签加分、或者在 `operator` 源里被人工确认后才启用。**
2. **契约赢过结构**。契约是发布方对"这个操作是什么"的**声明**；结构只是我们的推断。
   冲突时以声明为准，但要**用 probe 验证**（打开 `discovery_probe` 门），
   验证结果写进 `disputed` 记录——这样"客户文档写错了"会变成一条可查的事实，而不是一次静默误判。
3. **观测赢过契约**。真实流量是**行为证据**，比文档可靠。
   文档说"这里会回显参数"而三个月流量里从没回显过，那就不该拿它跑 XSS。

> **这三条的不对称是刻意的**：声明 > 推断，行为 > 声明。
> 但"行为"只在有足够样本时才算行为（`observed` 源要求至少 1 次真实记录，且不是本次任务自己产生的）。

**`disputed` 标签的使用限制**

| `disputed` 为 true 的标签 | 可否用于判定 | 报告标注 |
|---|---|---|
| 契约赢（C2） | 可以，但 `route_strength` 降一档 | 「契约声明与结构不符，已用探测验证」 |
| 观测赢（C4） | 可以 | 「以实际流量为准，文档已过时」 |
| 结构被忽略（C3） | — | 「结构上疑似 X 但契约未声明，未测」 |

最后一行是"诚实的未覆盖"：它比"测了但测错了"好得多，也比"没提"诚实。

## 4. 选择器匹配与排序（不是全跑，按风险排序）

```
match_score = 3×has_object_id_param + 2×is_admin_tag + 2×has_readonly_field
            + 1×has_uri_param + 1×is_token_issue + 0.5×param_count
            - 2×is_health_probe - 3×is_static_asset
```

| 规则 | 说明 |
|---|---|
| 只跑 Top-N | `policy.max_cases`（默认 200），其余进 `RouteSet` 但**不执行** |
| 同类去重 | 同 `(structural_key, oracle, param)` 保留最高分一条 |
| 稳定排序 | 同分按 `template_sha256` 字典序（**不是 op_id**：op_id 可能因契约顺序变化而变） |
| 覆盖均衡 | 每个标签至少取 1 条，避免全挤在一个业务域 |
| 空标签处理 | 某标签 0 命中 → 该 oracle 记 `NO_SELECTOR_MATCH`，进报告"未覆盖"清单，**不猜** |

**稳定排序用 `template_sha256` 的理由**：v2 用 `op_id` 字典序，但 `op_id` 来自契约的
`operationId`，客户改一下命名就全乱——这会让 `bench` 的 diff 噪声极大。
模板哈希只取决于结构，改命名不影响。

**标签记录的字段（每条标签都带，进 `OperationSet`）**

```python
@dataclass(frozen=True)
class TagAssignment:
    tag: str                      # 18 §6 字典里的词
    source: Literal["contract", "structural", "observed", "operator"]
    tag_confidence: float          # 按 §3.1 裁决表
    disputed: bool = False         # 有冲突且已裁决
    conflict: str | None = None    # "C2 契约∧结构冲突" 等，便于审计
```

**为什么标签要带置信度**：`route_strength` 由"绑定的 confidence"决定（`27 §3.3`），
而绑定的 confidence 里含 `param_ambiguity`——它的输入正是标签的 `tag_confidence`。
所以标签的不确定性会一路传导到报告的措辞强度（`09 §3.1`）。这条链必须不断。

## 5. 产出格式

### 5.1 `OperationSet`（契约解析结果，落 `out/contract/<sha>.json`）

```yaml
contract_sha256: sha256:...
operations:
  - op_id: <derived>            # 由 parser 生成，不含路径
    structural_key: sha256:...  # sha256(method | normalized_template | param_name_set)
    method: GET
    params:
      - {name: <p1>, in: path, type: integer, required: true}
    security: {requires: primary}
    semantic_tags: [object_read, param_injectable]
    tag_sources: {object_read: structural, param_injectable: structural}
    success_shape: {ct: json, has_field: "*id*"}
    score: 8.5
```

### 5.2 `RouteSet`（供 oracle 消费，见 `27 §3`）

```yaml
routeset_sha256: sha256:...
asset: web-01
bindings:
  - ref: route://contract/<opaque16>
    method: GET
    template_sha256: sha256:...
    param_schema: {...}
    semantic_tags: [object_read]
    auth_requirement: secondary
    source: contract
    sources_all: [contract, observed]
    confidence: 0.90
    ttl_s: 900
```

**人工可审**：`make cases-diff` 显示与上次的**结构差异**（新增/删除/标签变更/分数变化），
客户可以先审"要打哪些语义面"，再放行。审的是标签与分数，不是地址。

## 6. GraphQL 变体

| 步骤 | 做法 |
|---|---|
| 入口 | `graphql_endpoint` 标签（契约声明） |
| 获取结构 | introspection（被禁用则跳过，记 `INCONCLUSIVE`） |
| 标签映射 | query 的 `{id}` 参数 → `object_read`；mutation → `profile_write`/`admin_function` 按其 schema 判定 |
| 限制 | 单次查询深度 ≤3，防被当 DoS |
| 注意 | GraphQL 只有**一个**入口绑定；"打哪个 query"是 body 内容，不是路由。所以它的 router 粒度是 body operation，`RouteSet` 里只出现一条绑定 |

> 这条是 GraphQL 与 REST 的结构差异，必须在 `RouteSet` 里表达清楚：
> 一条绑定 + 多个 operation 名。`RouteCall` 的 `params` 里带 `operationName`。

## 7. 与 mTLS / 双账号的配合

| 场景 | 处理 |
|---|---|
| 每个 operation 需要不同角色 | `security` 声明 → `binding.auth_requirement`；缺角色则 `BLOCKED` 而非 `INCONCLUSIVE` |
| mTLS 必需 | 绑定带 `mtls: client_cert_ref`（来自 vault）；缺证书 → `BLOCKED` |
| token 有效期短 | 用例执行前刷新一次，任务内缓存（避免触发风控）；刷新走 `token_issue` 绑定 |

## 8. 实现约束（给 agent 的硬边界）

| 约束 | 值 |
|---|---|
| 纯函数 | 解析与打标签不联网；只读契约文件（位置由 routes 给） |
| 依赖 | `pyyaml` + `jsonschema`（不引入 openapi 全套 SDK，避免依赖爆炸） |
| 行数 | parser ≤400 行、planner ≤300 行、tagger ≤250 行 |
| 测试 | 3 份真实契约样本（含 `$ref`、含 3.1、含 GraphQL）各 ≥10 条断言 |
| 幂等 | 同输入两次生成，`routeset_sha256` 一致（排序稳定） |
| **零地址** | 本模块**不得** import `httpx`/`requests`；`import` 检查进 CI |

> 最后一条是机械保证：这个模块如果能发请求，就会有人拿它去"验证"路径。
> 它不需要网络能力，所以直接禁掉。

## 9. 验收（A7 断言）

1. 给一份含 40 个 operation 的真实契约 → 产出 `RouteSet`，**同输入两次 `routeset_sha256` 一致**。
2. 生成的绑定里，至少 5 条被 oracle 判 VERIFIED（真漏洞），0 条误报。
3. 契约自述的 host 不在 assets 解析集合 → 启动即拒（`VP-1006`）。
4. `make cases-diff` 能看出"新增 12 条 / 删除 3 条 / 标签变更 2 条"。
5. **契约里删除一个 operation → 对应绑定消失，依赖它的 oracle 变 `BLOCKED(route_unresolved)`，
   而不是报错、也不是继续打旧地址。**（这条同时验 A9.4）
6. `grep -rE "httpx|requests" veripen_contract/` 为空。
