# 20 · 认证体系测试点（JWT / OIDC / mTLS / Session / SAML）

> 车云普遍是 **mTLS + OAuth2/OIDC**，不只是账号密码。
> 本章把"认证体系怎么测"变成清单：每条标明**谁判定**（oracle / 人工 checklist），不假装全自动。

## 1. 分层视图

```
客户端 ──mTLS──▶ 网关 ──OIDC/OAuth2──▶ 授权服务 ──JWT──▶ 业务 API
                                          │
                                     会话/Refresh
```

**测试原则**：每一层都要有"正常路径 + 至少一个拒绝路径"的对照，否则判定不了。

## 2. JWT（自动化，归 `jwt_replay`）

| # | 测试点 | 变体 | 判定 | 自动化 |
|---|---|---|---|---|
| J1 | `alg=none` 可接受 | header `{"alg":"none"}` + 空签名 | 200 且返回受保护数据 | ✅ |
| J2 | 签名未校验 | 改 payload 保签名 | 200 且数据为篡改后主体 | ✅ |
| J3 | `sub` 可篡改提权 | `sub` 改为他人/管理员 | 返回特权数据 | ✅ |
| J4 | `role`/`scope` 可篡改 | 加 `admin` scope | 访问管理接口 200 | ✅ |
| J5 | `kid` 注入 | `kid=../../etc/passwd` / `kid=file:///dev/null` | 服务器报错或降级到空密钥 | ✅ |
| J6 | `jku`/`x5u` 外联 | 指向 OOB 域 | 收到回调（=可注入密钥） | ✅ |
| J7 | `exp` 未校验 | 过期 token | 仍 200 | ✅ |
| J8 | `nbf`/`iat` 未校验 | 未来签发 | 仍 200 | ✅ |
| J9 | 算法混淆（RS256→HS256） | 用公钥当 HMAC 密钥 | 200 | ✅ |
| J10 | 无签名段（两段式） | `header.payload.` | 200 | ✅ |

**共同判定**：`baseline 200 ∧ control（无效签名）401/403 ∧ 变体 200`。
J5/J6 若服务器 500 但泄露堆栈/路径，降级为 `INCONCLUSIVE` + 记 info 级发现。

### 2.1 J 系列的取证要求（判"是否发生"必须留三样东西）

J1–J10 都靠"变体 200"来判，但**200 本身不是证据**——很多接口对任何 token 都 200（返回一个空壳）。
所以每条 J 用例必须留三样，缺一即 `INCONCLUSIVE`：

| # | 必须有 | 为什么要 |
|---|---|---|
| ① | **变体的响应体含"只有该身份才能看到"的标记字段** | 证明"真的读到了别人/特权数据"，不是"接口回了 200" |
| ② | **同一变体在 control 下的完整 trace**（无效签名） | 证明"服务器确实在验签"，不是"什么都放行" |
| ③ | **token 的三段结构摘要**（header 的 alg、payload 的 claim 名、签名的长度与前缀） | 复现需要；但**不存签名原文**（`06 §4`） |

**"标记字段"怎么定**（这是最容易糊弄的地方）：

| 测试点 | 合法的标记字段 | 不合法的"证据" |
|---|---|---|
| J1/J2 | 响应里出现 baseline 那个账号的 `id`/`email`/`role` | `{"status":"ok"}` |
| J3 | 出现 `sub` 篡改后的目标身份标识 | 只看到 200 |
| J4 | 出现管理面独有的字段（如 `admin_actions[]`） | 只看到 200 |
| J7/J8 | 同 ①②③ 且 `exp`/`nbf` 值可读出 | 只看到 200 |

**规则**：标记字段必须是**契约里声明过的、且语义上只属于某一身份**的字段。
找不到这样的字段 → 该 J 用例记 `INCONCLUSIVE("no_discriminating_field")`，
**不许**用"200 就算"糊过去。这是 J 系列 FP 的唯一来源。

### 2.2 J 系列与 `Transform` 的对应（不需要新的 kind）

| 测试点 | 用哪个 `Transform` | `arg` 示例 |
|---|---|---|
| J1 `alg=none` | `replace`（target=header，字段 `alg`） | `"none"` + 签名段置空 |
| J2 改 payload 保签名 | `replace`（target=header，字段 `payload`） | 重新编码的 claim 段 |
| J3 `sub` 篡改 | `replace`（target=body_field，字段 `sub`） | 目标身份标识 |
| J4 `role` 篡改 | `append`（target=body_field，字段 `scope`） | `" admin"` |
| J5 `kid` 注入 | `replace`（target=header，字段 `kid`） | 相对路径载荷（`app §0.3` 允许的 `file:///` 形式） |
| J6 `jku` 外联 | `replace`（target=header，字段 `jku`） | `{{ref:OOB}}/{{nonce}}` |
| J9 算法混淆 | `replace`（target=header，字段 `alg`） | `"HS256"` + 用公钥当密钥重签 |
| J10 两段式 | `replace`（target=header，整体） | 去掉签名段 |

> 关键：**J 系列全部可以用既有的 8 种 kind 表达**。
> 若实现时想"加一个 `jwt_forge` kind"，说明它把"如何伪造"塞进了框架——
> 那是 oracle 的知识（`07 §6` 的分工铁律）。

## 3. OIDC / OAuth2（半自动，归 `oauth_flow` 检查单）

| # | 测试点 | 做法 | 判定 | 自动化 |
|---|---|---|---|---|
| O1 | `redirect_uri` 校验 | 改 `redirect_uri` 到 OOB 域 / 加路径后缀 / 用 `@` 混淆 | 是否跳转并带 code | ✅ 可自动 |
| O2 | `state` 缺失或可预测 | 去掉 state 重放授权请求 | 是否接受 | ✅ |
| O3 | `nonce` 未校验 | 重放 id_token | 是否接受 | ⚠️ 需解码 |
| O4 | PKCE 降级 | 有 challenge 时用 `plain` 或无 challenge 换 token | 是否成功 | ✅ |
| O5 | code 可重放 | 同一 code 换两次 token | 第二次是否成功 | ✅ |
| O6 | token 交换越权 | 用 A 的 code 换 B 的 token | 是否成功 | ⚠️ 需双账号 |
| O7 | 隐式流残留 | `response_type=token` | 是否仍支持 | ✅ |
| O8 | scope 提升 | 请求未授权 scope | 是否授予 | ✅ |

**判定方式**：O 系列多为"是否发生"，用**状态码 + 回调是否到达 + token 能否用**三条件。
无法确定时写 `INCONCLUSIVE` 并附原始响应，不猜。

**O 系列的三条取证纪律**

| 纪律 | 说明 |
|---|---|
| 回调必须落到 OOB 且 **nonce 可对** | 只看到 302 不算；要看 `Location` 里带出去的 code/state 是否真的到了我们的 OOB 记录 |
| **code 只能用一次**（O5） | 第二次失败才叫"正确"，第二次成功才叫漏洞。两次都要 trace |
| **token 必须真的能用**（O2/O4/O6） | 拿到 token 后打一次 `protected_read`。只看"返回了 token"不够——可能是空串 |

**最容易被糊弄的一条是 O1**：`redirect_uri` 被改成外域后，服务器可能返回 400 而不是 302，
但 400 的 body 里回显了 `redirect_uri` 原值。**那不算开放重定向**（`18 §1.5` 的 control 同理）：
判定只看 `Location` 头，不看 body 回显。

## 4. mTLS（半自动，归 `mtls_check` 检查单）

| # | 测试点 | 做法 | 判定 |
|---|---|---|---|
| M1 | 客户端证书缺失 | 不带证书直连 | 是否被拒（应 400/403 或 TLS 握手失败） |
| M2 | 过期证书 | 用已过期证书 | 是否被拒 |
| M3 | 自签/非受信 CA | 用自签证书 | 是否被拒 |
| M4 | SAN/CN 不匹配 | 证书 CN 与目标不符 | 是否被拒 |
| M5 | 弱签名算法 | SHA1 证书 | 是否被拒 |
| M6 | 证书吊销未检查 | 用已吊销证书（需 CRL/OCSP 环境） | 是否被拒 |
| M7 | 双向认证只验单向 | 服务端不请求客户端证书 | 无证书也能通 |

**自动化边界**：M1–M5、M7 可脚本化（自定义 SSLContext）；M6 需要 PKI 环境，标人工。

**M 系列的取证要点（TLS 层的信息不在 HTTP trace 里）**

| 要点 | 做法 |
|---|---|
| 握手失败要区分原因 | "certificate required" / "bad certificate" / "unknown ca" 是三件不同的事，不能都记成"被拒" |
| 必须记录**服务端是否请求了客户端证书** | 这是 M7 的判据：不请求 = 单向认证冒充双向 |
| 证书材料只存指纹 | `subject`/`issuer`/`serial`/`notAfter` + SHA-256 指纹；**私钥永不入 capsule** |
| 手工项要留"为什么手工" | M6 写"缺 CRL/OCSP 环境"，不是"太麻烦" |

**为什么握手失败要区分原因**：M1（不带证书）被拒是**正确行为**；
但如果拒绝原因是 "unknown ca" 而客户端用的是自签证书——那 M1 和 M3 测的是同一件事，
M1 实际上没被测到。混在一起会让"M1 通过"变成一句空话。
**注意**：M 系列一旦通过，说明整条链路的身份保证失效，severity 直接 critical。

## 5. Session / Cookie（自动化，归 `session_check`）

| # | 测试点 | 判定 |
|---|---|---|
| S1 | 会话固定（fixation） | 登录前后 session id 是否变化（不变 = 漏洞） |
| S2 | Cookie 标志 | `HttpOnly` / `Secure` / `SameSite` 缺失 |
| S3 | 登出未失效 | 登出后旧 cookie 仍可用 |
| S4 | 并发会话无上限 | 同一账号开 N 个会话全部有效（结合 rate_limit） |
| S5 | CSRF token 可预测/可复用 | 换会话后旧 token 仍被接受 |

**判定**：S1/S3/S5 是布尔；S2 是配置项（info/low）；S4 需阈值。

## 6. SAML（人工 checklist，本期不自动化）

| # | 测试点 | 说明 |
|---|---|---|
| X1 | 签名包裹（XSW） | 需要构造多断言 XML，工具化成本高 |
| X2 | XXE | 需解析器行为差异 |
| X3 | 断言重放 | 需 IdP 配合 |
| X4 | 未签名断言被接受 | 手工改 XML |

**本期结论**：SAML 只在报告里给 checklist 与"未覆盖"声明，不做自动判定。**诚实列出来比假装覆盖强。**

## 7. 与 profile 的接口

```yaml
auth:
  providers:
    - id: primary
      type: oauth2
      flow: authorization_code
      client_id: ...
      secret_ref: vault://demo-b/oauth-primary
      scopes: [read]
    - id: mtls
      type: mtls
      cert_ref: vault://demo-b/client-cert
      key_ref: vault://demo-b/client-key
  oidc:
    issuer_ref: IDP_ISSUER_REF          # 部署期注入的符号，不是地址
    redirect_ref: OAUTH_CALLBACK_REF    # 同上
  jwt:
    sample_token_ref: vault://demo-b/sample-jwt
```

**规则**：
- `secret_ref` 只出现引用；
- **`issuer` / `redirect_uri` 不得写地址**，一律用 `*_ref` 符号；
  符号在启动时解析，解析结果必须落在 scope 内，否则启动即失败（`VP-1006`）。
- 这一条与 `27` 同源：OIDC 的 issuer/redirect 是**最容易被称为"配置"而写进文档的地址**，
  所以显式改成引用。它同时解决了"测试环境与客户环境 issuer 不同"的问题。

**v3 变更说明**：v2 这里直接写了 issuer 与回调地址的字面值。
它们看起来像"配置示例"，但会被 agent 当作三个用途同时使用：文档示例、测试常量、profile 默认值。
现在它们只是符号——**代码、文档、报告里都不会出现真值**。

## 8. 覆盖矩阵（哪些自动、哪些人工）

| 体系 | 自动判定 | 半自动 | 人工 checklist | 本期覆盖 |
|---|---|---|---|---|
| JWT | 10/10 | — | — | ✅ 全 |
| OIDC/OAuth2 | 6/8 | 2 | — | ✅ 主要路径 |
| mTLS | 6/7 | 1 | — | ✅ 除吊销 |
| Session | 5/5 | — | — | ✅ 全 |
| SAML | 0 | — | 4 | ❌ 只给清单 |

**对外话术**：JWT/Session 全自动、OAuth2/mTLS 主要路径自动、SAML 人工——这个分级本身就是专业度。

**标签依赖（v3）**：OAuth2 相关的测试需要 `token_issue` 与 `redirect_entry` 两类标签；
mTLS 需要绑定带 `auth_requirement: mtls`。缺标签 → `SKIPPED(no_selector_match)`，进"未覆盖"清单。

## 9. 新增 oracle 的触发条件

| 触发 | 动作 |
|---|---|
| 客户使用 OAuth2 | 提 `oauth_flow` 为正式 oracle（把 §3 的 O 系列判定纯函数化） |
| 客户使用 mTLS | 提 `mtls_check` 为正式 oracle（TLS 层判定，需要自定义 transport 采集握手信息） |
| 客户使用 SAML | 进二期池，先出人工 checklist 模板 |

**本期**：JWT 走 `jwt_replay`；其余以"检查单 + 半自动脚本"交付，明确标注自动化程度。

**新增 oracle 的前置（v3）**：先确认 `18 §6` 里有它需要的标签；
没有就先加标签（改字典 + 靶场契约标注 + `tests/routes` 用例），再加 oracle。
这个顺序不能反——否则 oracle 会为了"能跑起来"而自己猜接口。
