# 36 · 插件市场与能力发现规格（v3.4 新增）

> **要解决的问题**：harness 的能力不该只有出厂那 14 个 oracle + 6 个 act。
> 用户应当能在 harness 里**像在 codex 里搜 GitHub 那样**，找到最新、最高星、真在用的开源安全能力，
> 装进自己的 harness——而且**必须比 DSH 更开放**：DSH 只能装自家市场的东西，我们要能吃 GitHub 上大部分
> 用 `npx` / `pip` / MCP 方式安装的安全类 skill 与 MCP server。
>
> **要避免的浪费**：每次刷新都全量重搜 + 又单独跑一遍已装插件的更新检查 = 两遍。本篇用**三层分离 + 增量刷新**解掉。

---

## 0. 一句话

> **发现（找新的）、注册（管已装的）、装配（接进哪一层）是三件事，各有各的缓存与时限。**
> 刷新时只补差量；找新能力和查旧插件版本**共用一次上游往返**，不重复。

---

## 1. 为什么必须分三层（先讲清失败模式）

如果把它们合成一个"刷新"按钮，会发生三件蠢事：

| 失败模式 | 后果 |
|---|---|
| 每次刷新全量重搜 | GitHub 搜索 API 有速率限制（未认证 10 req/min），点两下就 429 |
| 搜完再逐个查已装插件版本 | 已装 20 个插件 = 20 次请求，其中 18 个没变 |
| 搜索结果与已装清单混在一起 | "这个包有新版"和"有个新包"变成同一种提示，人分不清该干什么 |

所以：

```
┌─ 发现层 Discovery ──────────────────────────────────────┐
│  数据：search_index.json（按 query 缓存）                │
│  时限：TTL 24h（可配）；过期先给旧结果，后台增量补        │
│  问题：有没有我不知道的新东西？                          │
└─────────────────────────────────────────────────────────┘
┌─ 注册层 Registry ───────────────────────────────────────┐
│  数据：registry.json + lock.json（本地状态，永久）        │
│  时限：last_checked 冷却 6h                              │
│  问题：我装的东西有没有变？                              │
└─────────────────────────────────────────────────────────┘
┌─ 装配层 Assembly ───────────────────────────────────────┐
│  数据：scenario 字段 + policy.yaml（准入规则）            │
│  时限：加载即冻结，改动需重载                            │
│  问题：它能不能接、接进来能碰什么？                       │
└─────────────────────────────────────────────────────────┘
```

**一次"刷新"的真实动作顺序**（这是省掉两遍的关键）：

```
用户点 ⟳
  ├─ ① 发现层：对每个**有 active query** 的索引项，检查是否到期
  │     └─ 到期 → 只拉"新增页"（用 etag + 已知 repo 集合过滤）
  ├─ ② 注册层：对每个已装插件，检查 last_checked 冷却
  │     └─ 超过 6h → 复用 ① 的上游响应（同域名并发批次里拿）
  └─ ③ 合并成一份 UI 状态推给前端（SSE，接 `34 §2`）
```

**②复用①的上游响应**：如果发现层这轮已经打了 GitHub API，注册层的版本检查就用**同一批响应的头信息**（`ETag`/`Last-Modified`）判变化，不再单发请求。
只有注册层要查的仓库**不在**发现层的响应里，才单独发。

## 2. 发现层：搜索与排序

### 2.1 搜索语法

```
/plugin search <关键词>              # 默认搜 GitHub + npm 的安全类
/plugin search skill:pentest         # 只要 skill 类
/plugin search mcp:sqlmap            # 只要 MCP 类
/plugin search lang:python stars:>500 pushed:>2026-06-01
/plugin search --cached              # 只用本地索引（断网可用）
/plugin search --refresh             # 强制绕过 TTL（受速率限制保护）
```

### 2.2 索引结构（按 query 一条）

```jsonc
// .veripen/plugins/cache/search_index.json
{
  "version": 1,
  "queries": {
    "skill:pentest": {
      "query_hash": "sha256:9f2c...",
      "results": [
        {
          "id": "gh:owner/repo",
          "kind": "skill",
          "repo": "owner/repo",
          "stars": 3200,
          "pushed_at": "2026-10-28",
          "archived": false,
          "license": "MIT",
          "topics": ["security", "pentest", "llm"],
          "install": { "method": "raw", "spec": "skills/pentest.md" },
          "etag": "W/\"3f2a\"",
          "last_seen": "2026-11-01T10:00:00Z"
        }
      ],
      "fetched_at": "2026-11-01T10:00:00Z",
      "ttl_s": 86400,
      "next_check_at": "2026-11-02T10:00:00Z",
      "page_cursor": { "page": 3, "reached_end": false }
    }
  }
}
```

**`page_cursor` 是增量刷新的核心**：不从头搜，从上次翻到的位置往后补。

### 2.3 增量刷新协议（三种情况）

| 情况 | 判定 | 动作 | 成本 |
|---|---|---|---|
| **未过期** | `now < next_check_at` | 直接返回缓存，UI 标 `cached` | 0 请求 |
| **过期但未过期太久** | `now < next_check_at + 7d` | **先返回旧结果**（标 `possibly_stale`），后台补第一页 + 对 `results` 逐个比对 `pushed_at` | 1–2 请求 |
| **过期太久 / 用户强制** | 其他 | 全量搜一次（分页到 `page_cursor`） | N 请求（受限速保护） |

**"比对 `pushed_at`"怎么做**：不逐个查仓库，用**批量 GraphQL 查询**（一次拿 50 个 repo 的 `stargazerCount` + `pushedAt`）——
这是 GitHub 官方的批量口子，比 50 次 REST 便宜一个数量级。

### 2.4 排序公式（必须可复算，不许"感觉排"）

```
score = 3.0 × log10(stars + 1)
      + 2.0 × recency(pushed_at)        # ≤90d=1.0, ≤180d=0.6, ≤365d=0.3, else=0.1
      + 2.0 × topic_hit                 # 命中 security/pentest/offensive 等主题 = 1
      + 1.0 × has_license               # 有明确许可证
      + 1.0 × installable               # 有 npx/pip/mcp 明确入口
      - 5.0 × archived
      - 3.0 × no_license
      - 2.0 × stale_beyond_2y
```

| 规则 | 说明 |
|---|---|
| 同分排序 | `(id)` 字典序，**不用 stars**（避免同星数抖动） |
| 展示 | UI 默认按 `score` 降序，但**列标题显示 stars**——用户的心智模型是星数 |
| 可复算 | 给定同一份 `results` 快照，`score` 必须完全可复现 → 写一条单测锁定 |

**为什么不用"使用率"**：GitHub 没有可靠的"使用率"指标（`clone` 数不公开）。能拿到的只有 stars / forks / 最近提交。
所以**"高使用率"用 `recency + stars` 代理**，并在 UI 文案里写清"按星数与活跃度排序"，**不吹使用率**。

## 3. 注册层：已安装状态

### 3.1 两个文件

```
.veripen/plugins/
├─ registry.json     # 已装清单（唯一事实源，可读可改）
├─ lock.json         # 版本锁定（可复现：任何一次任务都能回到当时的插件版本）
├─ policy.yaml       # 准入规则（见 §4.2）
├─ cache/
│  ├─ search_index.json
│  └─ check_state.json
└─ installed/<id>/   # 实装位置
```

```jsonc
// registry.json
{
  "version": 1,
  "plugins": [
    {
      "id": "gh:owner/burp-mcp",
      "kind": "mcp",
      "scenario": "act",              // 挂载点：knowledge|act|source|oracle
      "installed_version": "1.2.3",
      "latest_known": "1.2.5",
      "source": { "type": "github", "repo": "owner/burp-mcp", "commit": "abc1234" },
      "install_method": "mcp",
      "enabled": true,
      "installed_at": "2026-10-20T09:12:00Z",
      "last_checked": "2026-10-31T18:00:00Z",
      "upstream_state": "present",     // present|deleted|unreachable
      "trust": "reviewed"              // auto|reviewed|signed
    }
  ]
}
```

```jsonc
// lock.json —— 可复现的最后一道锁
{
  "version": 1,
  "lock": {
    "gh:owner/burp-mcp": { "resolved": "1.2.3", "sha256": "9f2c..." },
    "gh:owner/owasp-notes": { "resolved": "2.0.1", "sha256": "..." }
  }
}
```

**`lock.json` 的作用**：`17 I8` 要求证据可追溯。一条 finding 诞生时用的是 `burp-mcp@1.2.3`，
三个月后上游发到 `1.2.9`——**重跑时必须能拿回 `1.2.3`**。没有 lock，可复现就是空话。

### 3.2 更新检查（带冷却的、复用发现层响应的）

```
/plugin update-check            # 只查不装
/plugin update <id> [--to 1.2.5]
/plugin update --all
/plugin rollback <id>           # 回到 lock.json 里的 resolved 版本
```

| 规则 | 值 | 理由 |
|---|---|---|
| 冷却 | `last_checked` 距今 < 6h → 跳过 | 防狂点刷爆 API |
| 响应复用 | 若本轮发现层已打过同 host，用同批响应 | **这是"不跑两遍"的实现** |
| 只写 `latest_known` | 不改 `installed_version` | 安装是显式动作 |
| 上游消失 | `upstream_state=deleted`，**不自动卸载** | 用户可能正在用它跑任务 |
| 网络失败 | 保留上次结论，标 `unreachable` | 不能因为断网就说"没更新" |

### 3.3 版本来源解析（三种生态）

| 生态 | 查新版本 | 查询地址（符号化，见 §5） |
|---|---|---|
| npm | `npm view <pkg> version` | `REGISTRY_NPM` |
| PyPI | `pip index versions <pkg>` | `REGISTRY_PYPI` |
| GitHub raw | 比 `commit sha` / `pushed_at` | `GITHUB_API` |
| MCP server | 上游声明的版本（`serverInfo.version`） | 由适配器在启动时读 |

## 4. 装配层：接进哪一层，能碰什么（安全核心）

### 4.1 四类挂载点

| 挂载点 | 允许能力 | **能碰判定吗** | 门槛 |
|---|---|---|---|
| **`knowledge`** | 向 L2 注入文档知识 | ❌ 永不 | 无（只读文本，抄 `35 §4` 的 knowledge 纪律） |
| **`act`** | 向 `act.*` 动作池增加一个工具 | ❌ 只能产 `Lead` | **必须沙箱 + 二进制白名单** |
| **`source`** | 增加一种 `route_discovery` 来源 | ⚠️ 能影响绑定 | **人工 review + 必过 N1/N2/N3/N6** |
| **`oracle`** | 增加一类判定 | ✅ **可以** | **签名 + review + 44 例 bench FP=0** |

**这张表是整个插件体系的安全边界**，也是它能"开放"却不"失控"的全部原因：
**装 100 个 knowledge 是安全的；装 1 个 oracle 是重流程。**

### 4.2 `policy.yaml`（准入规则，可改但改要有理由）

```yaml
# .veripen/plugins/policy.yaml
knowledge:
  allow_install: true
  sandbox: none
  review: none
  limits: { max_files: 50, max_bytes: 2MB }

act:
  allow_install: true
  sandbox: required          # 没有容器就不许装
  binary_whitelist: [curl, jq, nmap, nuclei, ffuf]
  review: first_run          # 首次运行产出的轨迹要人看一眼
  limits: { max_runtime_s: 300, max_output_bytes: 8MB }

source:
  allow_install: manual      # 不许一键装
  review: human
  must_satisfy: [N1, N2, N3, N6]
  must_have: tests/routes 用例 >= 3

oracle:
  allow_install: manual
  review: human + bench
  must_satisfy: [I1, I2, I4, I8]
  signature: required        # 插件包必须带签名清单
  bench_required: true       # 必须能在 44 例上跑出 FP=0
```

### 4.3 三种安装方式的适配器

| 适配器 | 支持 | 隔离方式 | 关键约束 |
|---|---|---|---|
| `adapters/npx.py` | `npx <pkg>@<ver>` | **容器内**，stdio 通信 | 传 `--no-install` 保证版本锁定；禁用 `postinstall` 脚本 |
| `adapters/pip.py` | `pip install` 到独立 venv | 独立 venv + 容器 | 只装 wheel，禁 `setup.py` 副作用（`--only-binary`） |
| `adapters/mcp.py` | MCP server（stdio / SSE） | 独立进程 | 只暴露 `tools`，**不暴露 `prompts`/`resources`**（后者可能注入上下文） |
| `adapters/raw.py` | GitHub 上的 Markdown skill | 只拷文本 | 无执行，风险最低 |

**所有适配器共用一条铁律（红线 P1）**：

> **插件进程永远不能直接访问目标。**
> 它只能通过 harness 的 `tools.http` 或沙箱发请求——否则 `05 §1` 的 scope 四处校验被绕过，`27 N3` 也随之失效。

实现方式：插件运行时的网络命名空间**默认无出网**，只有本机回环上的 harness 代理（`PROXY_LOOPBACK` 符号）可通；
`exec_tool` 类插件要出网，走 harness 代理，由代理做 scope 校验。

## 5. 地址不入库：插件描述符里的地址怎么处理

搜索结果与 `registry.json` 里**会**出现 `github.com/owner/repo` 这类 URL——这是**元数据**，不是扫描目标。

`27` 的规则是：**可执行目标地址不入库**。所以：

| 位置 | 允许 | 说明 |
|---|---|---|
| `search_index.json` / `registry.json` | ✅ URL 原样 | 这是"去哪装"，不是"打哪" |
| `policy.yaml` | ⚠️ 只允许**符号名**（`REGISTRY_NPM` / `GITHUB_API`） | 实际值在 `.env` |
| 插件运行时 | ❌ 不许含目标地址 | 与 `act.*` 同规则（`35 §5`） |

**`lint-noroute` 的例外处理**：给 `.veripen/plugins/**` 加**窄豁免**（只放行 `github.com` / `registry.npmjs.org` / `pypi.org` 三个 domain），
且豁免**写在 allowlist 里带理由**，不写死在代码里——这样它仍然是可审计的例外，不是暗门。

│                                                                  │

**UI 上必须体现的三件事**（否则用户会误判数据新鲜度）：

| 元素 | 为什么 |
|---|---|
| **缓存时间 + 下次自动检查** | 让人知道看到的不是实时数据 |
| **版本箭头 `1.2.3 → 1.2.5`** | 一眼看出哪些要更新，不用点进去 |
| **挂载点色标**（knowledge 绿 / act 黄 / source 橙 / oracle 红） | 风险等级可视化 |

## 7. 指标（怎么证明这套东西没在浪费）

| 指标 | 定义 | 门槛 |
|---|---|---|
| **刷新请求数** | 一次 ⟳ 打出的上游请求数 | **≤ 2**（无新查询时）；命中缓存 = 0 |
| **增量命中率** | 增量刷新复用已有结果的比例 | ≥ 0.8 |
| **更新检查冷却命中率** | 因 <6h 被跳过的插件数 / 总数 | 记录（高了说明用户在狂点，UI 该给提示） |
| **装配失败率** | 装完在 `policy` 校验里失败的比率 | < 0.1（高了说明搜索结果质量差） |
| **插件导致的越界** | 插件尝试直连目标被代理拦下的次数 | **必须 0**（>0 说明红线 P1 被破） |

## 8. 验收（B12.13 收尾）

| # | 断言 |
|---|---|
| 1 | 同一次刷新：发现层与注册层**共用上游响应**（断言请求数 ≤2） |
| 2 | 6h 内重复刷新 → **0 请求**，且 UI 明确显示缓存时间 |
| 3 | 已过期但未超 7d → 先返回旧结果并标 `possibly_stale`，后台补 |
| 4 | `score` 公式对同一快照**逐位可复现**（单测锁死） |
| 5 | 安装 `knowledge` 类：一键完成，不影响判定 |
| 6 | 安装 `oracle` 类：**必须过 44 例 bench FP=0**，否则拒装 |
| 7 | 插件试图直连目标 → 代理拦下并记事件（红线 P1 有测试） |
| 8 | 上游删除插件 → 标 `deleted`，**不自动卸载** |
| 9 | `rollback` 能回到 `lock.json` 的版本 |
| 10 | `lint-noroute` 对 `.veripen/plugins/**` 的豁免**只放行三个 domain**，且有 allowlist 理由 |

---

## 9. 明确不做

| 项 | 理由 |
|---|---|
| 插件自动升级 | 破坏可复现（`lock.json` 会失效） |
| 给插件开放 `prompts`/`resources` | 会把上下文注入面打开（`05 §9` 的 PC1–PC4 失去意义） |
| 插件直接连目标 | 红线 P1，见 §4.3 |
| 自建插件市场（上传/托管） | 我们要吃 GitHub 生态，不是再造一个 npm（`99` 新条目） |
| 用"下载量"排序 | GitHub 无可靠公开数据，改用 stars + recency 代理，并在 UI 写明 |

---

## 10. 一句话总结

> **发现是"查"，注册是"管"，装配是"门"。**
> 查的时候省请求（增量 + 复用），管的时候有冷却（6h），门的时候分级（knowledge 松、oracle 严）。
> 这样既"能像 codex 一样搜 GitHub"，又不会把 `27` 和 `17` 的两条命根子弄丢。
