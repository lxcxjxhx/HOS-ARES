## 2. 能直接拼的四件（改 ≤50 行）

### 零件 A · 三证据分级判定模型（来自 S3 `core/judge.js`）

| 项 | 内容 |
|---|---|
| 出处 | `hos-sec-engine/dist/src/core/judge.js:1-140`（532 行） |
| 结构 | `primary`（易受攻击目标）/ `hardened`（已修复）/ `latest`（最新）三份证据交叉 |
| 比我们强在哪 | 我们的 `probe ∧ baseline ∧ control` 是**一次请求内的三点**；它是**三个环境**的同一点 |
| 我们缺的 | **"修复后仍触发"这一条**（`stillCrashes → illegal`）。我们现在只有"对照被拒"，没有"打了补丁还在" |
| 落地 | `07 §0.2` 骨架扩展：`three_way_holds` 增加可选的第 4 条件 `hardened_absent`（仅当靶场提供 hardened 实例时启用） |
| 改造量 | 结构照抄；判据要改（它判"崩溃"，我们判"语义差分"）。**约 40 行** |
| 不变量 | 强化 I2（三条件）→ 变"三条件 + 可选硬化对照"，**不削弱** |
| 许可证风险 | 本仓库自有代码，无外部许可问题 |

**关键代码事实**（防止自欺：它不是 LLM）：

```javascript

analyzePrimaryEvidence(evidence, finding) {

  if (this.isInfrastructureFailure(evidence)) return { errorLevel: 'E3_infrastructure_failure', ... }
```

名字叫 `LLMJudge`，实现是规则引擎。**这正是我们要的形态**，也说明"名字不可信、必须读实现"。

### 零件 B · 输出归一化三件套（来自 S1 `sdk-tools.d.ts`）

| 项 | 内容 |
|---|---|
| 出处 | `sdk-tools.d.ts:3288-3300`（`BashOutput`）、`:232` `truncatedByTokenCap`、`:465` `truncated` |
| 结构 | ① `truncated: boolean` ② `persistedOutputPath` + `persistedOutputSize`（超大输出落盘）③ `returnCodeInterpretation`（非错误退出码的语义解释） |
| 比我们强在哪 | 我们 `08 §2` 只写"截断 4KB"，**没写"截断后完整内容去哪"**。它给了一个明确答案：落盘 + 给路径 |
| 落地 | `08 §2` 输出归一化表加两列：`persistedPath`、`returnCodeInterpretation`；capsule 的 `response` 块加 `persisted_ref`（可选） |
| 改造量 | 纯字段与语义，**约 20 行** |
| 不变量 | 无冲突；补的是 N5 的完整性（证据不因截断而丢失） |

**`returnCodeInterpretation` 的启发**：它解决"退出码 1 到底是失败还是正常"的问题。
我们有同样的问题——`oracle` 里 403 是"对照成功"还是"请求失败"？现在靠 oracle 自己判，
可以借这个字段把它变成**结构化的语义标注**，进 capsule 可审计。

### 零件 C · 沙箱的"危险开关"显式化（来自 S1）

| 项 | 内容 |
|---|---|
| 出处 | `sdk-tools.d.ts:818-820`（`dangerouslyDisableSandbox?: boolean`）、`:3280`（输出里回显"沙箱是否被绕过"） |
| 结构 | ① 沙箱默认开 ② 关闭必须用**名字里带 dangerously 的字段** ③ **输出里回显是否绕过** |
| 比我们强在哪 | 我们 `05` 有 `max_impact_class` 与审批门，但**没有"这一条命令绕过了沙箱"的运行时记录** |
| 落地 | `05 §6` 留痕表加 `sandbox_overridden: bool`；`06` capsule 的 `env` 加同名可选字段；`09` 报告对"绕过沙箱的动作"单独标注 |
| 改造量 | 字段 + 一条打卡逻辑，**约 30 行** |
| 不变量 | 强化 I5（fail-closed 的可审计性） |

**为什么这条值钱**：我们的审批门记录"谁批了什么动作"，但没记录"这个动作是否在隔离环境外执行"。
两者是不同的风险：**批准了写操作，但没批准在宿主上裸跑**。这个字段把两者分开。

### 零件 D · 两段式参数分发（来自 S2 `lib/bin.js`）

| 项 | 内容 |
|---|---|
| 出处 | `dsh/lib/bin.js:13-26`（注释）+ `resolveBoot()` |
| 结构 | launcher 只解析**自己拥有的** flag；遇到第一个不认识的就**把剩余全部原样交给内层 app**，由内层自己解析 |
| 比我们强在哪 | 我们 `08 §2` 的工具 schema 是"整包校验"：多一个字段就报错。它的做法是**分段所有权** |
| 落地 | `08 §2` 的工具参数校验改为两段：外层（我们拥有的：`oracle_id`/`route_ref`/`reason`）严格校验；内层（oracle 自己的 `params`）交给 `params_schema` 校验，**外层不解析内层** |
| 改造量 | 校验器拆两层，**约 45 行** |
| 不变量 | 强化 I4（模型不能塞入我们不认识的字段到外层） |

**具体收益**：现在模型如果把 `skip_guard: true` 塞进参数里，我们的整包校验会报错（好），
但如果 oracle 的 `params_schema` 是 `additionalProperties: true`，它会静默通过（坏）。
两段式让外层**永远只认自己那几个字段**，多出来的一律在进入 oracle 前就被拦。

## 4. 不能拼的四件（**反面教材，价值更高**）

### 反例 ① `mcp/router.js` 的 URL 模板注入（S3，506 行）

```javascript
// router.js:36-44
toolMappings: [
  { action: '发送 SQL 注入 payload', server: 'http-fetch', tool: 'http_post',
    inputTemplate: { url: '{target}', body: '{payload}' } },
]
```

| 问题 | 后果 |
|---|---|
| `url: '{target}'` 是**字符串插值**，target 是地址 | 这就是 `27 §8` 反例库第一条的现代形态 |
| `skillId → tools` 是**硬编码表** | 加一个 skill 就要改这张表，等于 `19` 的契约解析完全缺失 |
| 没有 `RouteRef` 概念 | 无法追溯"这个地址从哪来"，审计第四问（`05 §6`）答不出 |

**对我们的直接结论**：**`probe` / `crawl` 源的实现绝不能参考它的形态**。
它的存在证明"渗透 Agent 天然会写成这样"——这正是 `27` 要防的。

### 反例 ② `Sandbox` 类从未被调用（S3 `runtime/sandbox.js`，86 行）

```javascript
// sandbox.js:47-60
isHostAllowed(host) {
  if (this.config.networkAccess === 'none') throw new SecurityError('Network access is disabled');
  ...
  if (this.config.allowedHosts.length === 0) return true;   // ← 空列表 = 全放行
}
```

| 问题 | 后果 |
|---|---|
| `grep -r "isHostAllowed"` 除自身外**零命中** | 沙箱是装饰品，`fetch(url)` 直接发 |
| `allowedHosts.length === 0 → return true` | **fail-open**：没配置就等于不限制 |
| 无人调用 → 无人发现它是 fail-open | 安全代码不接进主路径，等于没有 |

**对我们的直接结论**（两条都进 `05`）：
1. **`guard` 必须在 `send()` 内部调**，不能"提供给调用方自行使用"（我们 `05 §1.0` 已写，这里得到了实证支持）。
2. **白名单空 ≠ 放行**，必须 `fail-closed`（我们 `05 §1` 已定；这里是反面印证）。

### 反例 ③ `tool-registry` 的 `web_fetch` 接受任意 url（S3）

```javascript
// tool-registry.js:117-140
name: 'web_fetch',
handler: async (params) => {
  const url = params.url;            // ← 无校验、无 scope、无 guard
  const response = await fetch(url, { headers });   // ← 直接发
```

**对我们的直接结论**：这正是"工具层不做判定、但也不做边界"的典型。
我们的 `tools.http` 签名只接受 `RouteBinding`（`27 N1`），从类型上就写不出这个 handler。

### 反例 ④ `agent-pool` / `coordinator` 无隔离（S3 `agents/`）

| 问题 | 后果 |
|---|---|
| `createAgentForTask` 只做 `new SubAgentImpl(id, name, skillId)` | 所有子 agent **共享同一进程、同一权限、同一网络** |
| 无 `isolation` 概念 | 对照 S1 的 `isolation: "worktree" \| "remote"`——Claude Code 有，这里没有 |
| 无审批、无预算传递 | 子 agent 可以无限跑 |

**对我们的直接结论**：S1 的 `isolation` 字段值 3 分（有 worktree/remote 两档），S3 值 0 分。
我们 `12 §1` 的三档部署正好对上 S1 的思路，不需要改。

## 8. 本次逆向的方法学收获（写进 `28`）

| 收获 | 说明 |
|---|---|
| **名字不可信，必须读实现** | `LLMJudge` 是规则引擎；`Sandbox` 是装饰品。两个名字都反着 |
| **"有没有被调用"比"写得对不对"更重要** | `grep` 调用点比读实现更快发现问题（`Sandbox` 就是零调用） |
| **反向价值 > 正向价值** | 4 件能拼的 vs 4 件反面教材，后者对设计的约束更强 |
| **同一产品内部会自相矛盾** | S3 的 `judge` 很严谨，`web_fetch` 很随意。这说明"模块级严谨"不等于"系统级安全" |

第 4 条是最值得记住的：它解释了为什么我们 `27` 要用**类型系统 + CI** 而不是"团队约定"——
同一份代码里，同一个人在不同模块的严谨程度都不一样，何况多人。
