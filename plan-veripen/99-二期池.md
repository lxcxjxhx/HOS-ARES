> 用法：任何"顺便也做一下"的念头，先在这里登记。**登记不等于同意**，只表示"被记住了"。
>
> **v3 新增两条纪律**：
> 1. 每条必须有**前置条件**（写"等 X 稳定"而不是"以后再说"），否则它永远不会被评估。

## 2. 会触碰不变量的四条，逐条说清代价

这四条不是"以后做"，是"做之前必须先改不变量"。它们需要 `17 §0` 的削弱记录 + driver 批准。

### P-02 时间盲注 → 触碰 I2（三条件合取）

| 项 | 说明 |
|---|---|
| 冲突点 | 时间盲注靠"响应延迟的统计差异"，**没有 control 能给出确定的期望值** |
| 现有 `three_way_holds` | 要求 `control.matches(expect)` 确定成立；统计型只能给"分布不重叠" |
| 若要做 | 需要新增 `expect: "statistical"` 分支，且**必须独立实现**（不能复用 oracle 的统计） |
| 代价 | `three_way_holds` 复杂度上升；FP 门槛需重估（统计型天然有假阳性率） |
| 结论 | 二期可以试，但**必须先证明统计型也有 `expect` 可判**，否则就是给 FP 开后门 |

### P-05 路径词表爆破 → 触碰 I5（scope 边界）

| 项 | 说明 |
|---|---|
| 冲突点 | 词表爆破会请求大量"系统可能不认识的面"，它的目的不是验证已知面 |
| 现有边界 | `05 §8` 把"路径爆破找洞"明确列为不做 |
| 若要做 | 必须有独立门（`discovery_probe`）+ 独立预算 + 独立报告章节（"扫描型发现"） |
| 代价 | 客户合同要新增条款；OPEC 风险（把客户目标打挂）显著上升 |
| 结论 | 本期已经有受审的 `probe` 源（小词表），**扩大规模**是二期的事 |

### P-10 多 agent 编排 → 触碰 I4（模型不参与判定）—— **v3.2 已解，移出二期池**

| 项 | 说明 |
|---|---|
| 冲突点 | 多角色编排天然要求"角色间协商结论"，协商就是模型参与判定 |
| 现有铁律 | finding 只能由 `run_oracle` 产生（`08 §7`） |
| **解法（v3.2 已落）** | 用**类型**而不是纪律：`TaskSuggestion` 的 schema 里**没有** `verdict/severity/confidence` 字段，agent 间物理上传不了结论 |
| 落地 | `21 §3.5` + 批次 `B12.5`；DoD 是 `test_agents_cannot_negotiate_verdict` + 单/多 agent finding 集合差为空 |
| **残留代价** | ① 故障面增加（一个 Verifier 崩了任务要能继续，靠 B12.5 DoD#4 兜）② 上下文重复读（靠 `tokens_multi ≤ 1.3×` 兜）③ **不能并行写操作类 oracle**（会互相污染状态） |
| 结论 | **本期做（B12.5），形态冻结为"分工不协商"**。任何"agent 投票/协商结论"的提议一律打回 |

### P-14 可写前端 → 触碰 I8（只增不改 / 只读）

| 项 | 说明 |
|---|---|
| 冲突点 | 可写前端意味着人可以在 UI 里改发现状态、改 verdict |
| 现有铁律 | 报告渲染期断言 + capsule 不可变 |
| 若要做 | 所有写操作必须落成**新事件**（feedback），不得改 capsule/finding 本体 |
| 代价 | 需要 feedback 事件表 + 重渲染链路 |
| 结论 | 四期可做，但"写"只能是"追加判定"，不是"覆盖证据" |

## 4. 需求怎么进池（三步，缺一不许进）

```
1 写清"为什么现在不做"——必须是约束（时间/前置/风险），不是"优先级低"
2 写清"前置条件"——必须是可观察的事实（"X 在 3 个客户上稳定"），不是"等有空"
3 标"触碰不变量"——会碰的，先走 17 §0 的削弱记录，再谈排期
```

**反例（会被打回）**：

| 写法 | 为什么不行 |
|---|---|
| "优先级低" | 优先级会变；约束不会 |
| "以后再说" | 无法评估，等于永远不做 |
| "顺手就做了" | 这正是范围失控的入口（`13 R1`） |
| "客户要的" | 客户要的写进合同，不写进池 |

## 5. 池子的健康度（每季度看一次）

| 指标 | 健康值 | 说明 |
|---|---|---|
| 池内条目数 | 15–25 | 太少说明没人提需求（或提了没记）；太多说明范围在膨胀 |
| 有前置条件的比例 | 100% | 缺前置 = 无法评估 |
| 触碰不变量的比例 | ≤ 20% | 高了说明"想做的"和"架构承诺的"在打架 |
| 一季度内被真正取出的 | ≥ 1 | 一条都取不出，说明池子只是垃圾桶 |
| 从池里删掉的（确认不做） | ≥ 1 | 只进不出 = 没有决策，只有堆积 |

**最后两行是这一节存在的理由**：需求池最坏的形态不是"太长"，是"只进不出"。
那样的池子和没有池子一样——区别只在于让人产生"我记下来了"的错觉。
