# 12 · 工程与交付（部署 / 离线 / 配置 / 版本 / 运维）

> 金句：**"客户差异只能进配置，不能进代码"** —— 这一条决定这套东西能不能卖第二家。
> 本章的目标是：客户现场装不上、跑不起来、看不出问题——这三种死法都被提前堵住。

## 1. 部署形态（三档，同一份镜像）

| 档位 | 场景 | 组成 |
|---|---|---|
| L 本地单机 | 演示 / POC | `docker compose up`：api + worker×3 + redis + sqlite + 靶场 |
| M 客户内网 | 交付 | 同上 + PG + 外部 Redis（客户提供）+ nginx 反代 |
| S 离线断网 | 高安全客户 | M 的全部镜像 `docker save` 成 tar，随包发布 |

**没有 K8s 档**（本期不做，理由写清楚：单客户 POC 的瓶颈是容器数不是编排器）。

## 2. 离线包（A3 断言的实现）

```
make package-offline
  → dist/veripen-<ver>-offline/
     ├─ images/{api,worker,redis,pg,dvwa,juice,crapi,vampi,webgoat,tsp-lab,oob,ollama}.tar
     ├─ install.sh          # docker load + 生成 .env + 建卷 + 首启自检
     ├─ uninstall.sh        # 保留数据，删容器
     ├─ profiles/           # 客户档样例（不含真实凭据）
     ├─ models/             # 可选：本地模型权重（sha256 校验）
     ├─ SHA256SUMS          # 全部文件
     └─ README.txt          # 三步安装 + 找谁
```

| 要求 | 规格 |
|---|---|
| 体积 | 无模型 ≤ 1.5 GB；含 7B 量化模型 ≤ 6 GB（提前告诉客户） |
| 校验 | `sha256sum -c SHA256SUMS` 必过，失败即停 |
| 依赖锁定 | `uv.lock` / `pip freeze` 全锁定；基础镜像用 digest 不用 tag |
| 幂等安装 | `install.sh` 可重复执行；已存在则跳过并提示 |
| 回滚 | 保留上一版目录，`install.sh --rollback` 一步切回 |
| 无外网假设 | 安装脚本里**不得有任何 curl 外网** |

## 2.5 依赖锁定清单（离线包能不能成，全看这张表）

| 类别 | 锁定项 | 规则 |
|---|---|---|
| 基础镜像 | `python:3.12-slim@sha256:...`、`redis:7.2-alpine@sha256:...`、`postgres:16-alpine@sha256:...` | **只用 digest**，禁 `latest`/浮动 tag |
| 靶场镜像 | `vulnerables/web-dvwa@sha256:...`、`bkimminich/juice-shop@sha256:...` | 同上；digest 记进 `tests/range/VERSIONS.md` |
| Python 依赖 | `uv.lock` 全量锁定（含间接依赖） | CI 用 `uv sync --frozen` |
| 模型 | Ollama 模型 + `sha256`；或网关地址 | 离线包把权重放 `models/`，可选 |
| 系统包 | 镜像内 `apt` 一律不装（slim 基础镜像够用） | 需要时写进 Dockerfile 并记版本 |
| 构建工具 | `uv` / `docker compose` 最低版本 | `doctor` 检查版本下限 |

**反例**：`pip install requests`（不锁版本）→ 半年后离线包重建，行为变了，bench 基线失效。

### 2.6 迁移脚本规范

```
migrations/
├─ 001_init.sql           建 6 张表 + 索引
├─ 002_add_replay_status.sql
└─ ...
```

| 规则 | 说明 |
|---|---|
| 只前进 | 不做 down 迁移（回滚靠备份 + 镜像回退） |
| 幂等 | 每条迁移有 `schema_migrations(version, applied_at)` 记录，重复执行跳过 |
| 版本校验 | 启动时比对代码要求的版本与库内版本，不一致报 `VP-7002` |
| 破坏性变更 | 必须先双写过渡（加新列 → 回填 → 切读 → 删旧列），分三个版本完成 |
| capsule 兼容 | capsule 是文件不是表，schema 升位后旧文件永久可读 |

**v3 迁移特别说明（002 起）**：`routesets` 与 `route_bindings` 是**过程表**，可以重建；
但 `capsules.routeset_sha256` 与 `route_ref` 是**证据字段**，一旦写入不可回填。
迁移时的处理：旧 capsule 这两列保持 `NULL`，并由 `render` 标注"无路由证据"（`24 §6` 兼容承诺）。
**不允许**用当前 routeset 回填历史 capsule——那是在伪造证据链。

## 3. `doctor`（16 项，覆盖到"地址从哪来"）

`make doctor [PROFILE=x] [--deep] [--audit --engagement E]`

| # | 检查项 | 失败提示 |
|---|---|---|
| 1 | docker / compose 可用与版本 | "需 Docker ≥ 24" |
| 2 | 端口占用（从 bindings 读出，不写死端口号） | 列出占用进程 |
| 3 | 镜像是否齐备（含 digest 匹配） | 缺哪个、怎么补（load 命令） |
| 4 | Redis 连通与授时（`TIME`） | "时钟不一致，回收会误判" |
| 5 | DB 可达 + 迁移版本 | "schema 版本 7，代码需要 8，跑 make migrate" |
| 6 | 模型连通（走 bindings 的 `model.health` op）或 scripted planner 可用 | "模型不可达，将以 scripted planner 运行（degraded）" |
| 7 | 靶场契约可达（不是探某个页面） | "<name> 契约未就绪，等 30s 或看 logs" |
| 8 | profile schema 校验 + 语义校验（`02 §3`） | 精确到字段路径 |
| 9 | **profile 零地址校验（`VP-1005`）** | "第 37 行出现可定位字面量" |
| 10 | scope 非空、deny 与 assets 无交集、窗口有效 | 逐条 |
| 11 | vault 密钥可解 | "VERIPEN_MASTER_KEY 未设置" |
| 12 | OOB listener 在线（符号解析 + 自测） | "ssrf_oob 将返回 INCONCLUSIVE" |
| 13 | **`bindings check`（每个 op_id 有绑定、每个 path_key 有值）** | "task.submit 的 path_key OPS_TASK_SUBMIT 未设" |
| 14 | 磁盘余量（capsule 会涨） | <2 GB 警告 |
| 15 | `--deep`：`03 §7` 的**十一条**一致性查询（含路由卫生五条 + 来源越界一条） | 逐条结果 |
| 16 | `--audit`：某 engagement 的请求留痕汇总 + **路由解析轨迹摘要** | 谁/何时/哪资产/证据路径/绑定来源分布 |

**设计原则**：doctor 只诊断不修复（除 `--fix-perms` 一类无风险项），且**输出可直接贴给客服**。

**为什么第 2 项不再写死端口号**：v2 的 doctor 检查"8000/6379/5432/80 是否被占"。
这四个数字本身就是硬编码——它们既是文档里的"知识"，也是代码里的常量。
现在端口从 `bindings` 读，doctor 说的是"API 端口（部署配置为 X）被 pid N 占用"。

## 4. 配置管理（客户差异的全部容器）

| 配置对象 | 位置 | 变更方式 |
|---|---|---|
| 客户档 | `profiles/<name>/*.yaml` | 加目录 + `make doctor` |
| oracle 参数 | profile `oracles.params` | 同上 |
| **路由选择器** | profile `routes.selectors` | 同上（**只写标签与形状，不写地址**） |
| **路由发现策略** | profile `routes.sources` / `ttl_s` / `max_rediscovery` | 同上 |
| **内部 API 绑定** | `config/bindings/service.yaml`（只含 `op_id → path_key`） | 改 yaml；值在 `.env` |
| **来源接入点** | `config/bindings/sources.yaml`（符号） | 改 yaml；值在 `.env` |
| 报告映射 | `veripen/report/mappings/*.yaml` | 加文件 |
| 系统提示词 | `veripen/agent/prompts/*.md`（带版本号） | Git + 版本号 |
| 运行时 env | `.env`（端口/密钥/模型地址/**所有 path_key 与接入点符号的实际值**） | 环境变量，不进 Git |
| 默认值 | 代码内常量，**profile 可覆盖** | 上线后只允许 profile 覆盖 |

**禁止**：把客户域名写进代码、写进测试、写进提示词样例、写进报告模板、写进 doctor 提示语。

## 5. 版本与灰度

| 对象 | 版本策略 | 回滚 |
|---|---|---|
| 代码镜像 | semver + git sha（`image_digest` 进 capsule） | 切回上一 digest |
| profile | `meta.version` + `profile_hash` | git revert，旧证据标 stale |
| oracle | `version`；语义变更升 minor | 保留旧版本可并行注册（`sqli_bool_diff@1.0.0`） |
| **resolver** | **`resolver_version`（进每次 RouteSet 与 capsule）** | **镜像内保留旧版本可执行**（证据要能三年后 replay） |
| **契约** | **`contract_sha256`（进 VERSIONS.md 与 routeset 关联）** | 恢复旧契约快照；bench 基线同步失效 |
| 提示词 | 带 `prompt_version`，进 Git | 同上 |
| 报告模板 | `template_ver` 进报告头 | 同上 |

**灰度方式（无 K8s 也能做）**：worker 加标签 `--canary`，调度器按比例把任务分给 canary（`policy.canary_ratio`）。出问题 `make canary-off` 立即回退。

**resolver 也要灰度**：它是"地址怎么来的"唯一实现，改它等于改所有 oracle 的输入。
所以 `policy.resolver_canary_ratio` 与 worker canary 同机制，但**默认 0**（不灰度，全量切换 + 回滚）。

## 6. 结构化日志

```json
{"ts":"2026-11-01T02:14:03.412Z","level":"info","svc":"worker","worker_id":"w-2",
 "task_id":"01JAB...","kind":"http","asset":"web-01","oracle":"idor_cross_account",
 "route_ref":"route://contract/7f3a2c11","template_sha256":"sha256:b1e7…",
 "elapsed_ms":41,"status":200,"ok":true,"trace_id":"..."}
```

| 规则 | 说明 |
|---|---|
| 全部 JSON 单行 | 便于 grep / jq / Loki |
| 敏感字段在 logger 层 redact | 不靠调用方 |
| **不记明文地址** | 记 `route_ref` + `template_sha256` + `path_rendered_sha256`（`23 §4`） |
| `trace_id` 贯穿 api→worker→tool | 一次请求能串起来 |
| 日志级别默认 info；`http` 明细用 debug | 生产不刷屏 |
| 保留 | 本地 7 天滚动；证据文件永久 |

## 7. 运维四件套（交付时给客户的"不写 200 页手册"版）

1. **一页速查**：5 条命令（`doctor / up / demo / replay / report`）+ 三个常见故障对应命令。
2. **playbook**：`装不上`、`跑不动`、`结果可疑`、`要停`、**`发现面消失了`** 五种场景的分步处置。
3. **10 分钟录像**：装 → 跑 → 看报告 → replay。（现场演示失败时的兜底素材）
4. **路由急救卡（v3 新增）**：`routes` / `routes-explain` / `routes-diff` / `routes refresh` 四条命令
   + "看到 UNRESOLVED 先查什么"三步。这一张卡的作用是：让客户 IT 在**不改我们代码**的前提下，
   自己能判断"是我们解析不到，还是他们真的下线了那个接口"。

## 8. 升级与兼容

| 变更 | 兼容策略 |
|---|---|
| 表结构 | 迁移脚本 `migrations/NNN_*.sql`，只前进；破坏性变更需双写过渡 |
| capsule schema | `capsule_version`；读旧版必须支持（证据要永久可读）；1.0 无 `route` 块标注"无路由证据" |
| profile schema | `apiVersion`；v1 → v2 提供 `veripen profile migrate`（**会删除 `resource_paths` 并报错要求改 selector**） |
| **RouteSet schema** | `resolver_version`；旧 routeset 由旧 resolver 重算（镜像保留旧版本） |
| **bindings** | `version` 字段；缺 `op_id` 启动即失败（`VP-7003`） |
| API | `op_id` 只加不删；字段只加不删 |

**profile v1 → v2 迁移必须"失败式"**：把 `resource_paths` 自动翻译成 selector 是错的
（它会把"地址"翻译成"猜出来的标签"）。正确做法是**报错并提示人工选标签**：

```
VP-1007 profile_migrate_needs_human:
  无法自动迁移 oracles.params.idor_cross_account.resource_paths
  请改为 routes.selectors 引用，并人工确认为哪一类语义面
```

## 9. 交付验收清单（打印出来逐项打勾）

```
[ ] 断网机器 install.sh 成功，doctor 全绿（16 项）
[ ] make bindings-check 通过（每个 op_id 有绑定、每个 path_key 有值）
[ ] make lint-noroute 0 命中（例外 ≤6 行且带理由）
[ ] make demo 出 3 条发现，全部 replay OK
[ ] make demo-alt 同镜像只换 YAML 跑通，core diff 为空
[ ] 缩 scope 后拒绝执行（退出码非 0，零请求）
[ ] lint-noleak 通过（core 无客户串）
[ ] bench.md 三轮 FP=0、越界=0、routeset 一致
[ ] report.sarif 通过 schema 校验；报告三视图零地址
[ ] verify-manifest / verify-chain / verify-capsule 全绿
[ ] kill worker 后任务被接管
[ ] make rediscovery-drill 通过（删绑定→重发现，无兜底）
[ ] 一页速查 + playbook + 录像 + 路由急救卡 已交付
```

**为什么清单变长了 3 项**：这 3 项（`bindings-check` / `lint-noroute` / `rediscovery-drill`）
是唯一能在交付前发现"硬路由又回来了"的三个检查。少一项，前面所有"零地址"的承诺都只是口头。
