# 16 · 完整范围与交付地图（v3 全量）

> v1.1 的"第一版合同"是**裁剪版**，它假设 agent 写不快、要保底。
> 修正后的事实：**agent 写代码很快，瓶颈在验证与集成**，所以不削范围，改削"批次粒度"。
> 本文是全量范围的唯一权威；"先做什么"看 `21-实现批次与Agent执行计划.md`，不再另设"第一版"裁剪。
>
> **v3 修正**：v2 的范围是全的，但**缺一层**——路由解析层。
> 没有它，全量范围里的每一个 oracle、每一份 profile、每一个靶场适配都会各自长出写死的路径。
> v3 把这一层显式列为 C0，并把"零地址"升为可演示断言 A9。

## 1. 范围原则（v3）

| 原则 | 含义 |
|---|---|
| 范围不削 | 14 类 oracle、3 worker、三视图报告、离线包、Web 只读控制台、双客户档、契约解析 —— 全做 |
| **地址不入库** | 代码/配置/提示词/报告/测试里都不出现可网络定位字面量（`27` N3） |
| 批次细化 | 18 个可独立验收批次（`21`），每批一条 DoD 命令 |
| 证据先行 | 每批 DoD 必须有可执行输出，没有"应该可以" |
| 内核零客户串 | 任何批次都不许往 `core/` 写客户信息（`lint-noleak` 守） |
| **重试即重发现** | 失败重试只能重新解析，不许换字面量（`27` N4） |

**"完整"的定义**：本文 §3 的 13 项能力全部有代码、有 DoD、有证据，且 `21` 的 18 批全 `done`。

## 7. Parking Lot（仍然不做，理由不变）

| 项 | 理由 |
|---|---|
| 业务逻辑类（改价 / 竞态 / 状态机跳步） | 需业务建模，二期；但**报告里要能讲"我们识别了但未覆盖"** |
| 时间盲注 | 抖动，需采样框架 |
| 白盒 SARIF in→out | 需 tree-sitter + 调用图，二期 |
| 交互式工具（msf / sliver） | 靶场不需要；交付给客户时按需加 |
| 多模态车机 | 另一条产品线 |
| SAML 全自动化 | 工具化成本高，本期给 checklist |
| 多租户 / RBAC / K8s | 第二个付费客户之后 |
| **路径爆破找洞** | 属"发现面"不属"验证漏洞"；只在 `probe` 源里以受审方式存在（`05 §8`） |
| **完全自动化的路由猜解** | 猜出来的面不能用于判定（`27 §3.3`），做深了收益低、风险高 |

## 9. 与 v2 的差异（一句话）

> v2 问"全量怎么拆才能让 agent 一批批吃掉而不失控"；
> v3 问"**吃掉之后，怎么保证它不会在某次'顺手'里把地址写死**"。
> 答案：把地址从类型系统里删掉，然后让 lint 与 bench 一起守着。
