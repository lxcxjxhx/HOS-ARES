# 09 · 报告与交付格式（三视图）

> 一份数据，三个读者：研发看细节、CI 看机读、合规看映射。
> 禁止三个格式各写一套逻辑——**全部从 `findings + capsules` 单向渲染**。
>
> **v3 变更**：
> 1. 报告正文**不含任何可网络定位字面量**（`make lint-noroute-report`）。
> 2. 每条发现必带 `route_ref`(前 8 位) + `route_source` + `route_strength`。
> 3. 新增"证据强度"维度，弱绑定自动降措辞（§3.1）。

## 1. 三视图与读者

| 视图 | 文件 | 读者 | 关键要求 |
|---|---|---|---|
| Markdown | `reports/<eng>.md` | 研发、甲方安全团队 | 每条发现可点回 capsule；措辞分级；**零地址** |
| SARIF 2.1.0 | `reports/<eng>.sarif` | CI / 代码扫描平台 / DefectDojo | `ruleId` 稳定、`fingerprints` 稳定、可去重 |
| JSON | `reports/<eng>.json` | 合规、二次加工、趋势统计 | 结构化、带合规映射章节、schema 校验 |

**同源性断言**：`report.json` 里的每条 finding 必须能在 `report.md` 与 `report.sarif` 中找到，反之亦然（`make lint-report` 校验）。

## 2. ruleId 规范（稳定 = 能进 CI 的全部前提）

```
veripen/<oracle_id>/<cwe>
例：veripen/sqli_bool_diff/CWE-89
    veripen/idor_cross_account/CWE-639
    veripen/ssrf_oob/CWE-918
    veripen/jwt_replay/CWE-347
```

| 规则 | 说明 |
|---|---|
| 不允许出现客户名/资产名/**路由/路径** | 否则同一类漏洞在不同客户产生不同 ruleId → CI 无法聚合 |
| oracle 语义变更 → `version` 升位，ruleId **不变** | 保持历史可比 |
| 新增 oracle → 新 ruleId | 老规则不消失 |
| 规则元数据（描述/帮助/标签）来自 `veripen_oracles/<id>/meta.yaml` | 集中维护 |

`rules[]` 段要求：`id`、`name`、`shortDescription`、`fullDescription`、`helpUri`（可为 `about:blank`）、`defaultConfiguration.level`、`properties.tags`（`security`、`cwe/89`、`owasp/wstg-INJECT`）。

## 3. 结果指纹（去重与回归的关键）

```json
"partialFingerprints": {
  "veripenFinding/v1": "<sha256(ruleId|asset_id|param_signature|oracle_version)>",
  "veripenRoute/v1":   "<sha256(ruleId|asset_id|param_signature|template_sha256|oracle_version)>"
}
```

- `param_signature`：发生漏洞的参数名+位置（如 `query:id`），**不含 payload 值**——这样同一洞第二次跑 payload 变了也不会被当新洞。
- **`veripenRoute/v1` 是 v3 新增**：它在指纹里加入 `template_sha256`。
  用途不同：
  - `veripenFinding/v1` 用于"这是不是同一个洞"（跨版本稳定）；
  - `veripenRoute/v1` 用于"这个洞所在的面有没有变"（端点改版时用来发现漂移）。
- CI 侧用前者做"新增 vs 已有"，用后者做"结构变更"提醒。**两者都不含地址。**

## 3.1 路由强度与措辞纪律（v3 新增，硬规则）

`route_strength` 来自 capsule 的绑定置信档（`27 §3.3`）。它决定这条发现能不能说重话：

| route_strength | 可用措辞 | 最高严重度 | 报告标注 |
|---|---|---|---|
| `observed` | 存在、可复现、已验证 | critical | — |
| `operator` / `contract` | 存在、可复现、已验证 | critical | — |
| `crawl` | 存在（需人工复核覆盖面） | medium | 「该面由可达性发现得到」 |
| `probe` | **可能**存在（无法确认） | low | 「该面由词表探测得到，未获契约佐证」 |

**渲染期断言**：`route_strength ∈ {crawl, probe}` 且 `severity ∈ {high, critical}` → 直接抛错、不出报告。

### 3.2 隔离外动作必须单独标注（借用 `29 零件 C`）

报告里凡有 `capsule.env.sandbox_overridden == true` 的发现，必须在**标题后**追加标记 `[未隔离执行]`，
并在附录列一张"隔离外动作清单"（资产 / 动作类别 / 审批人 / 次数）。

| 为什么单独标 | 说明 |
|---|---|
| 风险不同 | "批准了 3 个写请求"与"其中 1 个在宿主上裸跑"是两件事 |
| 审计需要 | 事后要能回答"有没有东西跑出过容器" |
| 客户会在意 | 这是甲方安全团队第一个会问的问题 |

**不标注的后果**：报告看起来一切合规，但实际有一次动作绕过了隔离——这是审计意义上的失真，
比误报更严重（误报只是不准，失真是不实）。
这是把"弱证据不许说大话"变成代码，而不是变成一句提醒。

> 为什么这条重要：渗透报告里最伤信任的是"高危"两个字后面跟着一个猜出来的路径。
> 弱绑定不是不能报，是**不许报成高危**。

## 4. Markdown 报告结构（模板固定）

```markdown
# <客户> 渗透验证报告
- 授权编号 / 测试窗口 / profile_hash / 镜像 digest / 报告 root_sha256
- routeset_sha256（前 12 位）× N / resolver 版本
- 一句话结论 + 统计块（发现数、按严重度、已验证/未能验证、复现通过率、按证据强度分布）

## 1. 摘要（管理层，<=1 页）
| 风险等级 | 数量 | 证据强度 | 最需要关注的 3 条 |
## 2. 已验证发现（每条一节）
### 2.1 <标题>  [HIGH] CWE-639 · 置信度 0.95 · 证据强度 契约
- 资产 / 面（`object_read` 语义 + route_ref 前 8 位）/ 账号角色
- 现象（一句话，不含"可能/疑似"）
- 证据：`capsule_id` `self_sha256` `replay_status` `replay_at`
- 复现：`veripen replay --capsule out/capsules/<id>.json`
- 影响与建议（分"立即可做"/"需排期"）
- 技术细节折叠块（请求/响应摘要，**地址以 route_ref 呈现**）
## 3. 未能验证（单列，措辞必须中性）
- 原因码：INCONCLUSIVE / BLOCKED(route_unresolved) / budget_exhausted / dead_letter
## 4. 覆盖范围与未覆盖（诚实清单）
- 已覆盖 oracle × 标签；**哪些标签 0 命中**（这才是"没打到的面"）
- 未覆盖 oracle 及原因（引 07 §5）
- **本次路由解析状况**：`routeset_sha256` 前 12 位、来源分布（contract/observed/crawl/probe）、
  **`sources_failed`**（哪个来源没取到，为什么）、`SKIPPED` 两类计数
- **弱证据面清单**（`route_strength ∈ {crawl, probe}`）：打到了但证据强度不够的面，逐条列出
## 5. 合规映射
- 每条发现 → 控制项（按 report.frameworks 渲染）
## 6. 附录：环境、时序、证据链校验结果、路由解析轨迹摘要
```

**措辞纪律（`make lint-report` 强制）**

| 状态 | 允许的动词 | 禁止的词 |
|---|---|---|
| VERIFIED（强绑定） | 存在、可复现、已验证 | 可能、疑似、建议关注 |
| VERIFIED（弱绑定） | 可能存在、需人工复核 | 存在、确认、高危 |
| UNVERIFIABLE | 无法确认、需人工复核 | 存在、确认 |
| BLOCKED | 按授权不可测试 / 当前环境下无该测试面 | 未发现（会被误读为安全） |
| **ROUTE_UNRESOLVED** | 该测试面已不存在 | 已修复（**这是最常见的误报**） |
| **ROUTE_DRIFT** | 该面结构已变更 | 已修复、未复现 |

**"未覆盖"与"未发现"必须分开写**：
- "未发现" = 测了，没有；
- "未覆盖" = 没测（因为无标签命中/未授权/路由解析不到）。

**再加一层（v3）："未覆盖"要能区分三种成因**

| 成因 | 报告写法 | 客户该做什么 |
|---|---|---|
| 无对应语义面（`no_selector_match`） | "该系统不提供此测试面" | 无需动作（设计如此） |
| 有面但解析不到（`route_unresolved`） | "存在疑似面但未解析成功" | 检查契约可达性 / 补适配契约 |
| 来源失败（`sources_failed`） | "契约不可达，本次只用观测面" | 查契约服务 / 补 credentials |

三种混成一句"未能覆盖"是最常见的敷衍——它让客户无法判断**是我们的问题还是他们的问题**。
把后者写成前者，等于用"打不到"冒充"很安全"。

## 5. 合规映射（车企口径，配置驱动）

| 框架 | 映射粒度 | 例 |
|---|---|---|
| OWASP WSTG | 测试项编号 | `WSTG-INPV-05` ← sqli |
| CWE | 弱点编号 | 直接由 oracle 提供 |
| ISO/SAE 21434 | 条款（威胁场景/风险评估） | 发现 → 威胁场景 → 风险等级 |
| UN R155 / R156 | 附件 5 威胁类别 | 越权 → "身份认证/授权失效"类 |
| GB 44495 / 44496 | 条款条目 | 同上 |
| 等保 2.0 | 控制项 | 访问控制、身份鉴别 |

**实现方式**：`veripen/report/mappings/<framework>.yaml`，纯数据，形如

```yaml
iso21434:
  CWE-639: {clause: "8.3 威胁场景分析", threat: "未授权访问车辆/用户数据", risk: high}
```

新增框架 = 加一个 yaml + 在 profile `report.frameworks` 里点名，**不改代码**。

## 6. 水印与防篡改

| 项 | 做法 |
|---|---|
| 水印 | 每页页脚 `root_sha256[:12] · <engagement> · <render_time> · <distribution>` |
| 页级哈希 | JSON 里给每节 `sha256`，便于局部校验 |
| 导出标记 | `distribution: internal|partner|customer` 决定水印文案与是否允许含 IP/域名 |
| 二次分发 | `--external` 时脱敏（IP 打码末段、域名保留、凭据全去、**`path_rendered` 整字段删除**）+ 加"对外版本"字样 |
| **地址剥离检查** | `--external` 出包后自动跑 `grep -E 'https?://|[0-9]{1,3}(\.[0-9]{1,3}){3}'`，非空即拒绝交付 |

## 7. 报告质量分（用于 bench 的 0.1 权重）

| 项 | 分值 | 判定方式 |
|---|---|---|
| 每条发现都有 capsule 且 replay_status≠NEVER | 0.3 | 断言 |
| 措辞合规（无禁用词、弱绑定不升级） | 0.2 | lint |
| 覆盖与未覆盖章节完整（含 0 命中标签） | 0.2 | 字段非空 |
| 合规映射存在且非占位 | 0.2 | 映射命中率 |
| **零地址（正文与 SARIF 均无）** | 0.1 | `lint-noroute-report` |

## 8. 交付物打包

```
dist/<engagement>/
├─ report.md / report.sarif / report.json
├─ capsules/            # 证据包（可分享，不含凭据、不含可用地址）
├─ routesets/           # 绑定集摘要（ref + source + confidence + template_sha256）
├─ bench.md             # 本次跑分
├─ manifest.json        # 文件清单 + 每个文件 sha256 + root_sha256
└─ README.txt           # 怎么读、怎么 replay、找谁
```

`manifest.json` 是交付的"封条"：客户拿到后 `veripen verify-manifest` 一条命令校验完整性。

**为什么把 `routesets/` 放进交付包**：客户需要知道"你们打到了哪些语义面、漏了哪些"。
放摘要不放模板，既满足可审计，又不泄露完整攻击面地图（`05 §7` 定级依据）。

## 9. 验收

1. 同一份数据渲染两次，除时间戳外字节一致（渲染确定性）。
2. 手改 `report.md` 一个数字 → `verify-manifest` 报失败。
3. SARIF 通过官方 schema 校验 + 在 GitHub Code Scanning 的本地 CLI（`sarif validate` 等价物）无告警。
4. 删掉一条 capsule → 渲染直接失败（不降级）。
5. **把一条发现的 `route_strength` 改成 `probe` 且 severity=`high` → 渲染抛错。**
6. **`grep -E 'https?://|[0-9]{1,3}(\.[0-9]{1,3}){3}' reports/*.md reports/*.sarif` 为空。**
7. **报告里存在"未覆盖"章节至少有 1 项 0 命中标签的条目**（演示诚实清单不是摆设）。
8. **"未覆盖"章节必须出现三种成因分列**（`no_selector_match` / `route_unresolved` / `sources_failed`），
   缺任一类字段即 lint 失败——即使本次那类计数为 0（要显式写 0）。
