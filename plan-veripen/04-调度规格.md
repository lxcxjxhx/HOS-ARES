# 04 · 调度规格（幂等 / 租约 / 重试 / 背压 / 死信）

> 分布式这块的考点不是共识，是**有副作用的动作如何不重复、不失控、不卡死**。
> 本文每条规则都对应一个可演示的失败场景。

## 1. 幂等：三层闸门

| 闸门 | 位置 | 防什么 |
|---|---|---|
| ① 请求幂等键 | `POST /tasks` 唯一索引 | 同一个人点两次、客户端重投 |
| ② 状态条件更新 | `transition(frm→to)` 带 `WHERE state=frm` | 两个 worker 同时拿到同一任务 |
| ③ 验证结果复用 | `ux_finding_run(task_id, oracle_id, asset_id)` | 同一任务内重试导致重复发包 |

```python
def submit(req) -> Task:
    key = sha256_canonical([req.engagement_id, req.asset_id,
                            sorted(req.oracle_ids), req.params])
    try:
        return store.insert_task(..., idem_key=key)
    except UniqueViolation:
        return store.get_by_idem_key(key)      # 直接返回已有结果，不重跑
```

**口号**：重复提交是常态，不是异常。

### 1.1 哪些动作允许"重发"（安全语义上的幂等）

| 动作 | 重发安全 | 处理 |
|---|---|---|
| GET / HEAD 变体请求 | ✅ | 可重试 |
| 登录/取 token | ⚠️ | 每任务只取一次，缓存到任务结束（避免触发账号风控） |
| 写类请求（本期只 read_only，不涉及） | ❌ | 一律走审批门，且 `idem_key` 含 nonce |
| OOB 回调监听 | ✅ | 按 nonce 去重，重复回调只记一次 |

## 2. 租约与心跳（数字见 03 §3）

```
worker 启动
  ├─ worker_id = host + pid + ulid
  ├─ 心跳线程：每 5s → 续租当前任务 + 写 heartbeat_at + 刷新 vp:hb:<worker> TTL=15s
  ├─ 领取循环：每次取 1 个 QUEUED（或清空后 sleep 1s）
  └─ 退出信号：SIGTERM → 释放租约（state 回 QUEUED，attempt 不 +1）
```

**关键细节**

| 细节 | 做法 | 原因 |
|---|---|---|
| 用谁的时钟 | **Redis `TIME`**，不用本机 | 多 worker 时钟漂移是回收误判第一杀手 |
| 续租失败 | 连续 2 次失败 → 完成当前 step 后停止领取 → 若已丢失租约直接 `os._exit` | 防双跑 |
| SIGTERM | 释放租约而不是让租约过期 | 让重排快 30s，演示更好看 |
| 任务内长操作 | 每 10s 主动续租一次（不只靠心跳线程） | 心跳线程可能被 GIL/阻塞 IO 饿死 |

## 3. 失败分类学（决定"要不要重试"）

```python
class ErrClass(str, Enum):
    RETRYABLE   = "retryable"    # 超时、连接重置、5xx、429、Redis 抖动、模型 5xx
    TERMINAL    = "terminal"     # 参数错、schema 校验失败、目标 404、oracle 不适用
    NEEDS_HUMAN = "needs_human"  # 需审批、凭据失效、疑似越界
```

| 错误 | 分类 | 动作 |
|---|---|---|
| `httpx.ConnectTimeout` / `ReadTimeout` | RETRYABLE | 退避重试 |
| 目标 5xx（且基线也 5xx） | RETRYABLE | 重试，但**基线失败判定为环境不可用**，不产出 finding |
| 目标 4xx | TERMINAL | 不重试（越权测试里的 403 是有意义的证据，要记录不是重试） |
| 429 | RETRYABLE | 尊重 `Retry-After`，且降全局令牌速率 30% |
| 模型 5xx/超时 | RETRYABLE | 降级链（见 08），3 次失败 → 任务 `DONE(部分)` 而非 FAILED |
| scope 校验失败 | **不可重试** | 立即 BLOCKED + `stop_on_scope_violation` 停整任务 |
| profile schema 错 | TERMINAL | 启动期就该拦住，运行期出现即 bug |

**退避**：`1s, 4s, 16s`（±20% 抖动），最多 3 次。抖动是为了避免 3 个 worker 同步重试打崩目标。

## 4. 顺序性

- 分区键 = `asset_id`。同一 `asset_id` 的任务串行（每资产并发 1 个任务），不同资产并行。
- 同一 `asset_id` 内的事件按 `seq` 严格递增（单 worker 单任务内天然有序，跨任务不保证）。
- **不做全局有序**：没有必要，也没有人需要。这是能讲"我们不需要 Consensus 也不需要全局序"的地方。

## 5. 背压与限流（三层，从粗到细）

```
第 1 层  全局 QPS 令牌桶        vp:rl:global   20/s, burst 40
第 2 层  每资产并发信号量        vp:sem:asset:<id>  2
第 3 层  目标自适应降速          目标连续 3 次 429/5xx → 该资产 QPS × 0.5（最低 1/s）
```

| 行为 | 规则 |
|---|---|
| 拿不到令牌 | **排队**（`max_throttle_wait_s=5`），超时记 `throttle_timeout` 并把该步标 INCONCLUSIVE，不丢任务 |
| 目标 429 | 全局降速 30%，持续 60s，记 `target_backoff` |
| 目标 5xx 连续 5 次 | 该资产熔断 5 分钟（`circuit_open`），任务转 `FAILED(retryable)` |
| 突发保护 | 单任务突发上限 = 10 请求/秒（防单个 oracle 放炮） |

> 一句话：**宁可慢，不可把客户目标打挂**——这是 OPSEC 的第一性要求。

## 6. 死信（dead_letter）

进入条件（任一）：`attempt ≥ 3` | `error_class=terminal` 且非客户可修正 | 连续 3 次 `scope BLOCKED`

处理：

| 项 | 做法 |
|---|---|
| 数据 | 保留全部 capsule（哪怕只是基线）与 `task_events` |
| 报告 | 单列「未能验证」章节，写明最后一次错误码与人为建议动作 |
| 重试入口 | `make requeue ID=<task>`（人工确认后重排，attempt 归零） |
| 监控 | 死信率 >5% 视为环境问题（靶场/凭据/网络），不是功能问题 |

## 7. 预算执行（不是软提醒，是硬刹车）

| 预算 | 检查点 | 到 80% | 到 100% |
|---|---|---|---|
| steps | 每 step 前 | 禁 explore，只允许 `run_oracle` / `finish` | 强制收敛，产出已得结果 |
| tokens | 每次模型调用前 | 关掉"读全文"类工具输出，改摘要 | 停止调用模型，走确定性收尾 |
| wall_clock | 每 step 前 | 优先跑剩余最短 oracle | 停止发包，渲染已得证据 |
| cost_usd | 每次调用后 | 降级到便宜模型（降级链末位） | 同 tokens |

**超预算的产出必须如实标注**：报告里写 `budget_exhausted: steps`，不写"已完成"。

## 8. 三个必须能现场演示的失败场景

| 场景 | 操作 | 期望 |
|---|---|---|
| 重复提交 | 连点两次 `POST /tasks` 同一个 key | 返回同一 task_id，`task_events` 只有一份 |
| worker 崩溃 | `docker kill worker-1` 执行中 | ≤35s 任务被另一 worker 接走，`attempt=1`，已产 capsule 复用 |
| 打得太快 | profile 里把 QPS 调到 200 打靶场 | 触发 429 → 自动降速 → 任务仍完成，日志有 `target_backoff` |
