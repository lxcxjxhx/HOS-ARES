# 23 · 可观测性与诊断

> 目标：任何时候都能回答**四问**——现在在干什么、为什么慢、为什么贵、**这个地址是从哪来的**。
> 不是搭一套监控平台，而是让 `make stats` 与 `make doctor` 说人话。
>
> **v3 变更**：stats 三表 → **四表**（新增重发现轨迹）；doctor 15 项 → **16 项**；
> 新增审计第四问的实现（`route.explain`）；日志与指标都不得记录明文地址。

## 1. 三类可观测数据

| 数据 | 位置 | 用途 | 保留 |
|---|---|---|---|
| 业务事件 | `task_events`（库） / `out/<task>/step.jsonl` | 每一步做了什么、耗时、token、**用了哪条绑定** | 90 天（导出 parquet 后清表） |
| **路由解析** | `routesets` + `route_bindings`（库） / `out/routes/<sha>.json`（含模板） | 这次任务能打哪些面、每面从哪来 | 30 天（被 capsule 引用的除外） |
| 请求留痕 | capsule + `out/capsules/bodies/` | 审计、replay | 永久（WORM 语义） |
| 运行日志 | stdout JSON（docker logs） | 故障定位、支持 | 本地 7 天滚动 |

**四者通过 `trace_id`、`task_id`、`routeset_sha256`、`route_ref` 互相跳转**，这是唯一的关联键。

**v3 红线**：日志、指标、stats 输出里**不得出现明文地址**。
需要标识一步请求时用 `route_ref`（不透明）+ `path_rendered_sha256`（可比对）。
只有 `out/routes/<sha>.json` 与 capsule 内部有模板，且它们受 `05 §7` 的定级与导出闸门约束。

## 2. `make stats TASK=<id>` 输出（四张表）

```
① 步耗时 Top5         seq=17 oracle=idor 842ms | seq=22 http 1.2s | ...
② token 分布          plan 38% / tool_out 21% / retry 12% / judge 0% / other 29%
③ 重试与降级          retry=2 (timeout×1, 5xx×1) | degrade=none | throttle_wait=3.4s
④ 重发现轨迹 ★        ref=route://contract/7f3a2c11 STALE@seq=9 → rediscover → ref=…9d63 (contract, 0.90)
                      ref=route://contract/8c44be0a NOT_FOUND@seq=14 → rediscover → UNRESOLVED (no candidate)
```

| 表 | 看什么 | 异常信号 |
|---|---|---|
| 步耗时 | 哪个 oracle 慢 | 单步 >10s → 查目标响应或网络 |
| token 分布 | 哪类消耗大 | `retry >20%` → 模型输出不稳定 |
| 重试降级 | 稳不稳 | `degrade≠none` → 模型/网关问题 |
| **重发现轨迹** | **系统迷路时怎么反应** | **同一 ref 连续 STALE ≥2 → 该端点不稳；UNRESOLVED 集中出现 → 契约/适配有问题** |

第 ④ 张表是 A9.4 的可读形态：它把"路由失效 → 重发现 → 结果"这条链变成一串能看的行。

## 3. `make stats ENG=<engagement>` 聚合（对交付有用）

| 指标 | 用途 |
|---|---|
| 每资产请求数 / QPS 峰值 | 证明没打挂客户 |
| 发现数 / 已验证率 / 平均置信度 | 质量画像 |
| 平均首发现步数 | 效率 |
| 总 token / 总成本 / 每发现成本 | 报价依据 |
| 死信率 / 越界次数 | 稳定性与安全性（越界必须 0） |
| **路由解析率**（有标签的例子里能解析到绑定的比例） | **discovery 是否退化**（`10 §3.2`） |
| **`SKIPPED` 分类计数**（`no_selector_match` vs `route_unresolved`） | 区分"没这个面"与"找不到面" |
| **平均重发现次数 / 任务** | 目标稳定性与 TTL 设定是否合理 |
| **绑定来源分布**（contract/observed/crawl/probe/operator） | 覆盖率是怎么来的 |
| **证据强度分布** | 有多少结论建立在弱证据上 |

后五项是 v3 新增。它们回答一个 v2 答不出的问题：
**"这次的覆盖率是靠契约、靠观测、还是靠猜？"**

## 4. 日志规范

```json
{"ts":"...","level":"info","svc":"worker","trace_id":"t-01J...","task_id":"01J...",
 "kind":"http","asset":"web-01","oracle":"idor_cross_account",
 "route_ref":"route://contract/7f3a2c11","routeset_sha256":"sha256:6d20…",
 "template_sha256":"sha256:b1e7…","elapsed_ms":41,
 "status":200,"ok":true,"error_class":null,"tool":"http"}
```

| 规则 | 说明 |
|---|---|
| 敏感字段在 logger 层 redact | `authorization|cookie|set-cookie|x-api-key|password` → `<redacted>` |
| **地址在 logger 层剔除** | 不记 `url`；记 `route_ref` + `template_sha256` + `path_rendered_sha256` |
| `level` 约定 | error=需人处理；warn=自动恢复但需关注；info=正常；debug=http 明细（默认关） |
| 不打印 body | body 只进 capsule，日志只记 `body_sha256` 与前 200 字符 |
| `error_class` 必填（失败时） | 对齐 `04 §3` 的**四分类**，便于统计 |

**为什么"不记 url"要写进日志规范**：日志是最容易被复制粘贴到工单/微信/文档里的东西。
一旦日志里有完整地址，它就会在三天内出现在某份 PPT 里——然后被当成"配置示例"进了代码。

## 5. `doctor` 的 16 项（见 12 §3，这里补充"说人话"要求）

| 失败时的输出必须包含 | 例 |
|---|---|
| 已查到的现象 | "端口被 pid 4242 (python) 占用" |
| 一条能直接复制的修复命令 | "kill 4242 或改 .env 的 API_PORT=<新端口>" |
| 跑完之后该做什么 | "改完执行 make up" |

**禁止**：`Error: connection refused`、`Traceback...` 这类无行动信息的输出。

**v3 新增第 16 项：路由卫生五查**（`03 §7` 的第 6–10 条）
输出形态必须是"查了什么 + 结果 + 不等于 0 时怎么修"，例如：

```
[16/16] 路由卫生
  ✓ VERIFIED 发现均含 route 块          0 异常
  ✓ 引用的 routeset 均存在              0 异常
  ✓ 弱绑定未标高危                      0 异常
  ✓ 重发现未超配额                      0 异常
  ✗ 绑定过期但任务仍在跑                2 条 → 跑 make routes refresh ASSET=<id>
```

## 6. 四个"必须能在 1 分钟内定位"的场景

| 场景 | 定位命令 | 期望输出 |
|---|---|---|
| 任务卡住 | `make stats TASK=x` 看最后一步 | 指出卡在 preflight（等令牌）/ 等审批 / http 超时 / **重发现** |
| 报告缺一条发现 | `make replay ID=n` | **七态之一** + 原因码 |
| 客户现场跑不起来 | `make doctor --deep` | 红项 + 修复命令 |
| **"这条发现的地址哪来的"**（v3） | `make routes-explain REF=<r>` | **来源链 + 置信度计算 + 解析时间 + 佐证证据 id** |

第四问是 v3 的核心可观测能力。它能回答客户最尖锐的问题：
"你怎么知道要打这个接口？"——答案是"契约里它被标注为 `object_read`，且有历史流量佐证"，
而不是"代码里写着"。

## 7. 指标埋点（不做 Prometheus，先做文件）

| 埋点 | 位置 | 频次 |
|---|---|---|
| `step_latency_ms` | task_events | 每步 |
| `tokens_total` | task_events.budget_json | 每步 |
| `throttle_wait_ms` | task_events(kind=throttle) | 每次排队 |
| `scope_denied` | task_events(kind=scope ok=0) | 每次 |
| `replay_status` | capsules | 每次 replay |
| **`route_resolve_ms`** | task_events(kind=route) | 每次解析 |
| **`rediscovery_count`** | task_events(kind=rediscovery) | 每次 |
| **`routeset_changed`** | task_events(kind=rediscovery, detail) | 每次（added/removed/changed 计数） |
| **`binding_confidence`** | task_events(kind=binding) | 每次使用绑定 |
| **`binding_source`** | 同上 | 每次 |

`make stats` 直接读这些，不引入时序库。**P2**：真需要趋势图再接 Prometheus。

## 8. 交付时的"可观测性承诺"（写给客户看）

| 承诺 | 证明方式 |
|---|---|
| 我们的每个请求都可追溯 | 任意发现 → capsule → 请求/响应/时间/IP |
| **我们知道每个请求的地址从哪来** | `routes-explain` 输出来源链与置信度 |
| 我们的速率受控 | `stats ENG` 输出 QPS 峰值曲线，不超合同 |
| 越界为零 | `bounds` 页为空，`doctor --deep` 第 5 条查询为 0 |
| **日志与报告里不含我们的内网路由图** | 报告零地址 + 日志不记 url |
| 出问题能复盘 | 日志 + 事件 + 证据 + **路由轨迹** 四件套，按 task_id 串起来 |

**第五条是 v2 没有的**，也是企业客户真正在意的：
他们要的是"你们测出了什么"，不是"你们把我们的内网结构抄走了一份"。
`06 §4` 的 `path_rendered` 导出剥离，就是这条承诺的实现。
